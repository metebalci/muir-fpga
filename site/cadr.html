The machine this project reproduces

The CADR is a 32-bit microcoded processor built at the MIT Artificial Intelligence Laboratory. It is the machine the Lisp Machine system was written for, and the design that the first commercial Lisp machines, from LMI and Symbolics, were built on.

It was designed around 1978, and the AI Laboratory published it as AI Memo 528, CADR, in 1980. The memo calls it "a general-purpose, 32-bit microprogrammable processor which is the basis of the Lisp-machine system, a new computer system being developed by the Laboratory as a high-performance, economical implementation of Lisp". It was a revised version of an earlier machine called CONS. The engineering drawings recovered from MIT's backup tapes were written between 1977 and 1981.

The memo is careful about two names that are often confused. The CADR machine is a design of microprocessor. The Lisp machine is the CADR machine plus the microcode that interprets the Lisp machine order code. One is hardware and the other is hardware with a particular program in it.

It is a machine for one person at a time. The display controller drives one screen, and the I/O board carries one keyboard and one mouse. Those three are the machine's own console, and the whole of the processor runs the work of whoever is sitting at it.

The processor was designed to emulate other instruction sets rather than to run Lisp directly. Its microcode interprets a 16-bit order code that the Lisp machine compiler produces. The memo says the design deliberately avoided wiring the Lisp machine's own instruction formats into the hardware, so that the software could change without the boards changing. What the hardware does offer is writable microcode, flexible dispatching and subroutining, good byte manipulation, and a stack kept inside the processor.

A CADR is not one board. The processor is two boards in a backplane of their own. The bus interface is a third board, in a cage that carries the machine's two buses, and everything else in the machine plugs into one of those two. Five flat cables join the processor to the bus interface. The sections below take them in turn.

The two processor boards

The processor is two large boards, and MIT's own print sets name them. The CADR section carries the data paths. The ICMEM section carries the control memory. Their wire lists are separate files and their drawings are separate print sets, but they are one processor and the netlist built from them is one file of 985 parts.

The CADR section holds the A and M scratchpads, the pushdown buffer and the microcode return stack, the ALU, the shifter and the byte hardware, the Q register, the memory address and memory data registers, the dispatch memory and both levels of the virtual memory map. The ICMEM section holds the control store, the boot PROM that overlays the bottom of it, the clock generator, the eight-deep history of the microprogram counter, the statistics counter, and the registers a console writes to halt and step the machine.

The microinstruction

A microinstruction is 48 bits wide. Every one of them names two sources, called A and M, and two of the four classes also name a destination. The class is two bits, IR<44:43>, and there are four of them.

  • ALU. The destination takes the result of a boolean or arithmetic operation on the two sources.
  • BYTE. The destination takes a byte extraction, a byte deposit or a selective field substitution from one source into the other. The field may be any non-zero width.
  • JUMP. Control transfers, conditionally on any bit reachable on the M bus or on a variety of internal conditions, page faults and pending interrupts among them.
  • DISPATCH. Control transfers to a place named by a word of the dispatch memory, selected by a field of up to seven bits taken from the M bus.

Two functional destinations make a microinstruction's fields variable, which is how the microcode reaches a computed scratchpad address or a computed rotation count. They are conceptual registers, together called the OA register, and what is written to one of them is ORed into the next instruction as it comes out of the control store. One covers the low 26 bits and the other the high 22. Only one half of an instruction can be modified this way, because the two cannot be written at once. Parity checking is disabled for an instruction modified like this, because the OR happens before the check.

Three bits are the same in every class. IR<46> counts the instruction in the statistics counter, which can stop the machine when it overflows. IR<45> is ILONG and runs the read phase of the clock long. IR<42> is POPJ, which returns from a microsubroutine after one more instruction has run.

The microcycle

The processor has one clock signal, and every edge-triggered register on the board takes one edge per microcycle. Between the edges the clock is a level, and the board reads it as one. In the read phase the scratchpads are addressed by the instruction's own source fields and the ALU settles. In the write phase the address changes to the write address left by the previous instruction, and the write pulse fires.

The cycle is of variable length. The read phase is set by the instruction's ILONG bit and by two speed bits in the mode register, which select four taps of a delay line. The four speeds give microcycles of 135, 145, 160 and 220 nanoseconds. Normal speed is 145 ns.

The clock can also stop, in two different ways, and the difference matters. A wait stops it at the end of the read phase, leaving the scratchpad latches open. The processor's clock stops and the clock to the bus interface and the Xbus devices keeps running, so they go on working while the processor stands still. A hang stops it at the end of the write phase, and is used only for memory reads. Both clocks stop together for a hang, so they restart in step with no extra delay. The effect is that the processor's speed matches the memory's exactly.

The control store

The control store holds 16,384 microinstructions of 48 bits. The microprogram counter is fourteen bits, which is what sets that size. The store is writable, and the microcode loads itself off the disk at every boot.

How the microcode writes it is a trick, and the memo says the odd shape of the instruction set here is the trick's fault. A JUMP with both its R and P bits set is a WRITE. It behaves like a call to the address being modified, so the old PC goes on the return stack and the PC register takes the address. Then, where the control store would have fetched the instruction at that address, a write pulse fires instead and the A and M sources are written into the store. The machine simultaneously behaves as though it had executed a return, pops the PC back, and carries on. The write costs a word of the return stack and an extra cycle.

The bottom 1,024 words are overlaid by the boot PROM while the mode register's PROMDISABLE bit is clear. The PROM is twelve 74S472 chips of 512 by 8, two banks of 512 words, and the page that decodes it makes the enable from the top four bits of the PC being zero.

The scratchpads and the pushdown buffer

The A bus is driven only from the A scratchpad, 1,024 words of 32 bits. The M bus is driven from the M scratchpad, 32 words of 32 bits, and from a variety of other internal registers. The M scratchpad is a copy of the first 32 locations of the A scratchpad, so the two are written together.

The memories are 93425As and have no clock pin. What holds a word between the two phases is a 74S373 latch beside each memory, not the memory itself. A scratchpad write is therefore one microcycle behind the instruction that computed the word, and the hardware hides that with pass-around paths: comparators match the instruction's source address against the write address still pending, and put the pending word on the bus instead of the memory's output. The A and M memories have those paths. The pushdown buffer does not, and the memo explains why: a cycle that writes the pushdown buffer must write the M scratchpad too, so the next instruction can use the M path instead.

The pushdown buffer is 1,024 words of 32 bits with a pointer and an index of ten bits each. It holds the top of the emulated stack, in the manner of a cache. The memo says this is worth the hardware because a large part of a Lisp machine's memory references are to the stack.

The sequencer and the dispatch memory

The microprogram counter is fourteen bits and behaves much like a conventional program counter. Beside it is a 32-location microcode subroutine return stack, with its own five-bit pointer and a pass-around path of its own for returns, which makes a two-instruction subroutine possible.

The dispatch memory is 2,048 words of seventeen bits. A DISPATCH instruction takes an M source, rotates it left by a rotation count, masks all but the low bits of it, and ORs what is left with the instruction's own dispatch address to make an eleven-bit address. The word it finds there is a fourteen-bit PC and three transfer bits: one pops the new PC off the return stack, one pushes a return onto it, and one inhibits the next instruction. A DISPATCH can also write the memory instead of reading it, which is how the microcode loads its own dispatch tables.

A dispatch can take its lowest address bit from the map instead of from the rotated field, with the map addressed by the memory data register. The memo says this is chiefly for testing a pointer just fetched from memory against the garbage collector's conventions.

An eight-deep shift register records the PC of each of the last eight instructions. MIT calls it the OPCs, and it is what a console reads to reconstruct how a halted machine got where it is.

The virtual memory map

Memory is reached through a two-level paging system that maps a 24-bit virtual address into a 22-bit physical one. A page is 256 words, so the low eight bits of the address pass through untranslated.

The first level is 2,048 entries of five bits, addressed by VMA<23:13>. Its output joins VMA<12:8> to address the second level, which is 1,024 entries of 24 bits. The top two bits of a second-level word are the access code and the fourteen bits under them are the physical page.

There is no state in the map. Both levels are asynchronous RAM chained combinationally, so a lookup is a ripple through two memories inside one microcycle. The access code is what refuses a read or a write, and the refusal reaches the microcode as a page fault that a JUMP can test.

Parity

Every internal memory in the machine is parity checked. Bad parity halts the machine if error halting is enabled, and the machine completes the current instruction and clocks the next one into the instruction register before it stops. So one wrong instruction will have run and the bad data is no longer on the buses, which is what the eight-deep PC history is for. Error halting is off at power-on and the bootstrap turns it on once it has filled every memory with good parity.

The data paths themselves carry no redundant checking. Instead the bootstrap runs simple diagnostics over the memories and the data paths before it trusts them.

The five cables, and the bus interface

The bus interface is its own board in its own backplane. MIT's parts list heads it "LISPM Bus Interface" and it runs to 33 sheets. Its own description of how it is attached is short and is worth having exactly:

"The bus interface plugs into the Xbus and the Unibus, and is connected to the cpu by 5 40-wire (alternating grounds) flat cables, which carry two independent busses and the master clock, which is supplied by the cpu to the bus interface."

Alternating grounds means twenty signals in a forty-wire cable. Read off MIT's wire lists, the five cables pair 92 signal wires between the two ends. Four of them leave the CADR section and one leaves the ICMEM section. Forty-eight of the 92 are driven from both ends, and they are exactly the two data buses: MEM<31:0> and SPY<15:0>.

The memory bus

The first of the two buses on the cables is the memory bus. The processor sends -MEMRQ, a level held while it wants a cycle, WRCYC high to write, and a 22-bit address. The address arrives already translated, because the map is on the processor board. The interface sends back -MEMACK, -LOADMD, which strobes the word into the memory data register, and -MEMGRANT. The 32 data lines go both ways.

The diagnostic bus

The second is the diagnostic bus, and the bus interface is its master. Its signals are sixteen bidirectional data lines, four address lines that select one of sixteen 16-bit diagnostic registers, and a read strobe and a write strobe. The registers themselves are on the processor boards.

Those four address lines follow the Unibus address, so the sixteen registers appear at Unibus 0o766000 to 0o766036. Reading and writing at one address are unrelated: there are sixteen readable registers and eight writable ones, and a readable and a writable register at the same address have nothing to do with each other. The readable set is the instruction register in three halves, the PC, the OPC history, both halves of the output bus, two flag registers, the A and M scratchpads in halves, and the statistics counter in halves. The writable set includes the mode register, the clock control register, the OPC control register and the debug instruction register.

This is what a console program drives, and the machine uses it on itself during bootstrapping.

The Xbus

The Xbus is the machine's 32-bit data bus. Main memory is on it, and so are the high speed peripherals: the disk controller and the display. It is open collector and terminated at both ends, 390 ohms to ground and 180 ohms to five volts at each end, which is an effective 123 ohm termination and a 56 milliamp load for a driver to pull down.

Transfers are asynchronous as far as the devices are concerned. A read puts the address and its parity on the bus, lowers -XBUS.RQ, and waits for the device to drive the data and assert -XBUS.ACK. The acknowledgement stays asserted until the master removes the request. Deskewing is the master's job: it must have good address, write and data lines up 80 nanoseconds before it lowers the request, and it must wait 50 nanoseconds after the acknowledgement before it strobes the data. A device that cannot produce parity, such as a register on an I/O board, asserts -XBUS.IGNPAR and the master does not check.

Arbitration is the one part that is not asynchronous. A device that wants the bus asserts -XBUS.EXTRQ and a grant is daisy chained from device to device along the backplane. Whether a device passes the grant on, and the moment it becomes bus master, are both clocked by a master clock distributed on the -XBUS.SYNC line. That clock is the processor's own, sent down the cables.

The Unibus

The Unibus is an ordinary PDP-11 Unibus, and it is there to attach peripherals, especially commercial devices built for the PDP-11 line. It is sixteen bits wide and every line is open collector, low when asserted and pulled up at rest. A master puts the address up, asserts -MSYN, and the slave answers -SSYN with the word or having taken it.

The bus interface arbitrates the Unibus when there is no PDP-11 on it, which on a Lisp Machine there generally is not. It also carries the interrupt paths: both buses can interrupt the processor, and the interface passes both.

What happens when nothing answers

A cycle that no device answers is given up on. The interface has a timer for it, a small PROM walked one state per tick of an oscillator on the board, and when it reaches its last state the interface sets a bit in its error status register and completes the cycle. There is a bit for an Xbus cycle that timed out and a bit for a Unibus one. MIT's own listing of that PROM gives ten microseconds for an ordinary cycle and a longer count for one arriving from the other processor over the debug cable.

The Unibus map

A Unibus master can reach Xbus memory, and it has to be mapped to do it, because the Unibus address space is not big enough to name it. The interface holds sixteen map registers at Unibus 0o766140 to 0o766176. Bit 15 of a register turns mapping on for that page, bit 14 allows a write from the Unibus, and the rest is the physical page number.

The window those registers translate is Unibus 0o140000 to 0o177777. Four bits of the address choose the map register, eight choose the word within the page, and one chooses which half of the word, because a 32-bit Lisp machine word is two Unibus words and the low half has the lower Unibus address. The interface buffers the halves so that two 16-bit accesses become one 32-bit cycle.

The interface's own Unibus block runs from 0o766000 to 0o766176 and is split four ways: the sixteen diagnostic registers, an interrupt and error status block, a debug block that the debug cable answers, and the sixteen map registers.

Main memory

Main memory is boards on the Xbus. One board is 65,536 words of 32 bits, built as four banks of 4116 dynamic RAMs. Every board is the same board, and an address switch on each one puts it at its place in the physical address space. Each board runs its own oscillator and refreshes itself, so nothing in the processor has to.

The physical address is 22 bits, so the Xbus can carry four million words. A machine with thirty-two boards has two million, which is what the System 100 release expects.

Memory parity is checked, and the mode flags in the diagnostic interface decide what happens when it fails: the machine can halt, the microcode can take a trap, or it can be ignored.

The disk controller and the Trident drives

The disk controller is one board on the Xbus, and it is a bus master as well as a slave: it moves blocks into main memory itself rather than handing them to the processor a word at a time. The drives are Century Data Trident disk packs in cabinets on the end of its cable.

The register face

The controller presents four 32-bit registers on the Xbus at physical 0o17377774 to 0o17377777, just below the Unibus. Reading and writing the same register are two different registers, as on the diagnostic bus.

The disk address is one word holding the unit in bits 30 to 28, then the cylinder, the head and the block. Three bits of unit is why one controller can address eight drives. A board called the disk multiplexor sits between the controller and the drives and fans out the nine signals that are per-unit, while the eighteen shared ones go past it to every drive.

Writing the command register does not start anything, which the controller's documentation points out is unlike most disk controllers. A transfer begins when something is written to START, after the other registers have been set up. The commands are read, read compare, write, read all, write all, seek, at ease, recalibrate, fault clear, offset clear and reset. Reset is the exception to the rule: it takes effect as soon as it is stored in the command register.

An operation that runs longer than about two and a half seconds is stopped with a timeout error. The timer is an oscillator on the board counted down by a pair of counters, and it runs whenever the controller is active.

The command list

A transfer is not one block to one place. The command list pointer names a list in main memory, and the controller walks it. Each word of the list is a channel command word: a physical page number, and a bit that says whether another command word follows. The controller fetches a command word, moves one block into the page it names, advances the heads to the next block, and fetches the next command word. So a single START can move a run of blocks into a run of unrelated physical pages, which is what a paging system wants.

What a block carries

A block is 256 words, which is one Lisp Machine page and 1,024 bytes. The drive carries three more words for each block beyond its data: a header word, a checkword over the header, and a checkword over the data. The controller compares the header against the address it was told to read under a mask, runs the header through an error-correcting code, and checks the data's checkword. Each of those has a bit of its own in the status register, and a soft data error leaves the burst pattern and its bit position in register 3 for the software to apply.

The two geometries

The controller was used with two drives. A T-80 has 815 cylinders, 5 heads and 16 or 17 blocks a track depending on how it is formatted. A T-300 has the same cylinders and the same blocks a track with 19 heads. Formatted at 17 blocks a track, a T-300 holds 263,245 blocks, which is 257 MiB.

Block 0 of a pack holds its label. The label begins with the word LABL and gives the geometry and the partition table, and a CADR reads it before it can do anything else with the pack.

The display board and the screen

MIT's word for the display controller is the TV. The board this project reproduces is the SIMPLE TV, the standard black-and-white one, which the window system asks for by name. A colour board called the LISPM TV replaced it in 1980.

The screen is 768 pixels across and 963 lines down, one bit a pixel. A line is 24 words of 32 bits. The frame buffer is a window of 32,768 words on the Xbus at physical 0o17000000, of which the picture uses 23,112. There is no colour and no grey. The picture is exactly what the software has written into those words.

Eight control words sit at physical 0o17377760, and only the first four do anything. Register 0 is the mode register. Registers 1, 2 and 3 are the data, the pointer and the enable of a RAM holding the sync program, which the software loads and reads back at every reinitialisation. The top four control words answer the bus and do nothing.

The mode register has four writable bits: two clock mode bits, a black-on-white bit that displays one bits as black and zeros as white, and an interrupt enable. Bit 4 is the vertical flag, a flip-flop of its own. It is set at the start of a frame, and a write of the register puts the written bit into it, which is how the microcode clears it. The flag and the enable together drive the Xbus interrupt line.

That is the vertical interrupt, and it is the machine's roughly-sixty-cycle clock. A frame is 966 lines of 16.000 microseconds, 15,456,000 nanoseconds, which is 64.7 hertz. The microcode hangs its mouse tracking and its scheduler's periodic work off it.

An Xbus reset clears the vertical flag and nothing else on the board. The mode register and the sync enable clear on a power reset, which is a backplane wire the processor raises only when the power comes on.

The I/O board

The I/O board is the machine's other half of a conversation with a person. It is a Unibus board, and it carries the keyboard, the mouse, two clocks and the status register they share, the serial port, and the Chaosnet interface. MIT drew the Chaosnet half as its own set of sheets, but it is one board and forty-seven signals cross between the halves.

The board answers Unibus 0o764000 to 0o764176, split into eight groups of eight addresses. The first four groups go nowhere.

The keyboard and the mouse

The keyboard is at 0o764100 and 0o764102, the low and high halves of a 24-bit word shifted in by three 74LS164s. A word arriving sets KBD READY. A read of the low half clears that flag and a read of the high half does not, which is why the microcode's interrupt handler reads the high half first. A word arriving on one that has not been read replaces it.

The mouse is at 0o764104 and 0o764106: Y with the three switches above it, and X with the raw quadrature lines above it, twelve bits of count on each axis. Seven lines come in from the mouse, four of quadrature and three of switches. They are latched twice, eight microseconds apart, and compared. Any difference sets MOUSE READY. A read of Y clears that flag and a read of X does not. Each axis's direction is one old line exclusive-ored with the other new one, and a step is counted only when exactly one line of the pair moved, so a mouse moved faster than the sample clock loses counts.

There is a beep at 0o764110 with no value in it. The address is not gated by the write signal, so a read clicks as a write does, and it toggles a flip-flop. One reference is one edge of a square wave, and the pitch is whatever rate the microcode references it at.

The status register at 0o764112 puts eight bits on the bus: four interrupt enables, the three ready flags, and the serial port's enable. Nothing drives the upper byte, so it reads as ones. Five bits can be written.

The clocks

The microsecond clock is at 0o764120 and 0o764122. It is a 32-bit counter driven by a 32 MHz crystal divided down, and it is latched: reading the low half latches all 32 bits as the counter stood at the start of the bus cycle, and the high half is that latch rather than the counter. It starts when the power comes on and no Unibus reset stops it.

0o764124 is two different registers. Written, it is an interval timer: four counters loaded from the bus that count down on a 16 microsecond clock and set CLOCK READY when they borrow. Read, it is a sixty-cycle clock, a pair of counters that have counted mains cycles since power-on and have their clears tied to ground.

0o764126 is a general-purpose port with nothing wired to it. It answers, and it reads as ones.

The serial port and the Chaosnet

The serial port is at 0o764160 to 0o764176. It is a Signetics 2651 with its own 5.0688 MHz baud-rate crystal beside it and an MC1488 and MC1489 out to an RS-232 connector. The chip is conditioned to transmit on CTS and to receive on DCD, so a device that carries bytes but does not raise the modem control lines gets nothing. The rate and the character frame are whatever the machine programmed into the chip.

The Chaosnet interface is at 0o764140 to 0o764156. It is the five registers of the Chaosnet memo's section 7, two packet buffers of 256 words each, one for transmit and one for receive, a bit counter and a lost count. Its own address comes off switches on the board. Its decode is subtle and the subtlety is MIT's: the decoder looks at read against write as well as at address bits, so one address is a different register depending on the direction of the cycle.

The interrupts

The card has four interrupt vectors and one grant chain. A latch takes the four requests at the grant, and two gates turn them into the low bits of the vector, so the vectors are 0o260 for the keyboard and mouse, which share one, 0o264 for the serial port, 0o270 for the Chaosnet and 0o274 for the clock. With more than one pending the clock is named first, then the Chaosnet, then the serial port, then the keyboard. Each request is a ready bit ANDed with its own enable.

A Unibus reset reaches five flip-flops and the 2651 and nothing else. KBD READY, MOUSE READY, the mouse counters, the interval timer and the microsecond counter have no connection to it and carry on.

The keyboard, and the light panel

A key is a position

The Lisp Machine keyboard sends positions, not characters. Its own firmware says so: "All key-encoding, including hacking of shifts, will be done in software in the central machine, not in the keyboard. Note that both pressing and releasing a key send a code, therefore the central machine knows the status of all keys."

So there are no modifier bits in a key event. Shift, Control, Meta, Super, Hyper, Top, Greek and the rest are keys at positions of their own, and the microcode works out what was meant from the stream of downs and ups. The keyboard this project models is MIT's new keyboard of November 1980, which has 31 named keys and 11 shifting keys.

What travels down the cable is 24 bits, low-order bit first, with a low start bit on a line that is high when idle. Bits 23 to 19 are ones, bits 18 to 16 are a source identifier that says which kind of keyboard this is, bit 8 is set for a key coming up and clear for one going down, and the low bits are the position. A separate word, marked by bit 15, reports that all keys are up, with one bit for each shifting key still held.

The keyboard also boots the machine. Its firmware watches for Control and Meta held together with Rubout or with Return, and when it sees the combination it sends a boot word instead of an ordinary key code. The I/O board recognises that word and pulls the processor's boot line. The character typed along with the combination is left where the bootstrap can read it, so the person at the keyboard can choose between a cold boot and a warm one.

The light panel

A CADR has a small panel of lamps and one button, on a cable from the processor's control memory board. The drawing marks its connector "TO LIGHT PANEL", and the wire list says what is on it: eleven signals, and the rest of the connector unused.

  • The boot button. One wire, grounded by a push button. The memo describes it as the diagnostic display panel starting a bootstrap "by grounding one wire".
  • The run lamp. One wire, carrying MACHRUN, which is the signal that lets the clock reach the data paths. Lit means the machine is running.
  • Nine parity lamps. One for each memory that is checked: the A scratchpad, the M scratchpad, the pushdown buffer, the microcode stack, the dispatch memory, the control memory, main memory, and each of the two levels of the map. The same nine signals are bits of the first flag register, where a console reads them.

The processor board has a display of its own beside that. Five TIL309 LED digits show the microprogram counter in octal, and the decimal point of each digit is wired to a status lamp: two lamps that gather the parity errors into groups, the dispatch memory's, the control memory's, and one that says the boot PROM is enabled. The bootstrap uses them: if its self-test fails it goes into a loop, and the PC standing in the lights says which test it was.

The debug cable, and CC

A CADR is debugged by another CADR. The debugger's DBGOUT connector goes to the debuggee's DBGIN connector over MIT's debug cable, twenty-one wires, and over it one machine's Unibus cycles run on the other machine's bus. The console program that does the debugging is called CC, and it is Lisp software running on the debugging machine.

The memo describes the arrangement more generally: the diagnostic interface lets "a unibus operator, such as a pdp10, a pdp11, or another lisp machine" control the machine. Another Lisp machine is what MIT actually used.

The cable carries a request line, two address bits, a write line and sixteen bidirectional data lines one way, and an acknowledgement the other. The two address bits are bits 3 and 2 of the debugger's own Unibus cycle into the debug block at 0o766100, and the debuggee decodes them into four strobes.

StrobeWhat the debuggee does
-DB NEED UBruns a cycle on the debuggee's own Unibus at the address last latched
-DB READ STATUSdrives the debuggee's error status onto the low byte of the data lines
-DB ADR1 CLKclocks three bits into the modifier register
-DB ADR0 CLKclocks sixteen bits into the address latches

Nothing on this cable carries meaning by an edge alone. Every wire is held for the whole of a request, and the request itself falls one delay-line section after the other lines are already standing, so the levels are settled before the debuggee looks at them. The latches take the data at the trailing edge of their strobe, which is when the request lifts, so the levels have to be standing then too.

Once a debug cycle can run on the debuggee's Unibus, everything on that bus is reachable. The sixteen diagnostic registers are there, so the debugger can halt the machine, single-step it and read the PC, the instruction register, the output bus and the flags. Main memory is there too, through the debuggee's own Unibus map, which is what the mapped window exists for. And the modifier register carries a bit that boots the debuggee, which is the third of the ways a CADR can be started.

Forcing an instruction

The diagnostic registers do not reach the machine's own memories. There is no register that reads the A scratchpad at an arbitrary address, or the pushdown buffer, or the control store. CC reads them anyway, and the way it does is the interesting part of the design.

The processor has a debug instruction register: six 74S374s holding 48 bits, which a console writes sixteen bits at a time into three of the writable diagnostic addresses. The clock control register has a bit called IDEBUG that puts that register on the instruction bus in place of the control store. So a console can compose any microinstruction it likes, load it, and clock the machine one microcycle with that instruction forced in.

To read A memory location 3, CC builds an instruction whose A source is 3 and whose destination is harmless, forces it in, steps one microcycle, and reads the output bus out of the diagnostic registers. The machine reads its own scratchpad for the debugger. The same trick reaches the M scratchpad, the pushdown buffer and the micro-stack, and a write is the same thing with the sources and destination the other way round.

The boot PROM

When a CADR is powered on it resets itself and the Unibus and does not start. RUN is clear and the clock does not reach the data paths. What starts it is a boot signal, and the memo lists the ways one can arrive: the diagnostic interface can command one, the light panel's push button grounds a wire, the bus interface can ground a wire, the Chaosnet interface pushes the button when it receives a certain sequence of messages from the network, and the I/O board recognises the keyboard's boot combination.

Whichever it is, the sequence is the same. The machine is reset, which halts it if it was running. RUN is turned on, which does nothing yet because the clock is stopped. The speed is set to the slowest, parity traps, error halts and the statistics counter are disabled, and the PROM is enabled over the bottom of the control store. The trailing edge of the boot signal lets the clock start, and control arrives at location 0 of the PROM.

MIT's source for that program survives, with its comments. It opens by saying that there are many places in it where cycles are wasted, deliberately, "since it is far more important that code in a PROM be bug-free than that the boot sequence be 150 nanoseconds faster". The program is version 9 and uses 454 of the 1,024 words the board decodes.

What it does, in order:

  • Makes itself a zero and a word of all ones without depending on any memory, then runs short diagnostics: that the ALU and the shifter drop and pick no bits, that the M and A memories agree, that every carry in the ALU carries, and that the byte hardware works a little.
  • Clears every internal memory, so that they all hold good parity. The control store is 16,384 words and it writes them all.
  • Generates a reset on both buses.
  • Sets up the map. It writes one entry of the first level and reads it back, then makes four pages: page 0 onto the first page of main memory, page 1 onto the disk controller's registers, page 2 onto the diagnostic registers at 0o766000, and page 3 onto the second page of main memory, which is where the system communication area lives.
  • Reads and rewrites every word of physical page 0, to give it good parity before the disk is asked to save it.
  • Turns parity checking on, by writing to the mode register through the map.
  • Recalibrates the disk, then saves physical page 0 onto block 1 of the pack and reads it back with a read compare, so that loading the microcode does not destroy it.
  • Reads block 0, the label, into page 0. It checks that the first word is LABL, takes the drive's geometry out of it, and finds the microcode partition.
  • Reads the microcode partition and loads it. The file in that partition is a series of sections, each starting with three words: a section type, a starting address and a count. Type 1 is the control store, 2 the dispatch memory, 3 main memory and 4 the A and M memories.
  • Reads page 0 back off block 1 to undo the save, and copies the pushdown buffer into the A and M memories, which is how it loads those two without a pass-around path.
  • Turns the PROM off and enters the real world. It writes to a Unibus address in the diagnostic block that sets both error-stop enable and PROM disable, and jumps to location 6. The PROM and the microcode that has just been loaded share a common loop at that location, waiting for the Unibus cycle to happen, so the machine walks out of the PROM and into its own microcode at the same instruction.

If something goes wrong there is a halt for it, and MIT put a no-op before each one so that the halts fall at even addresses and the two possible values in the PC lights differ only in the low bit. A bad label, a bad address in a section, a disk error: each stops the machine somewhere the light panel can be read.

The source's own list of work still to be done has one entry: loading the microcode over the Chaosnet.

Sources

Nothing on this page is a first-hand invention. Every claim is read from one of the documents below. MIT's own files are committed unmodified in muir's mit/ directory, which has an inventory of what each one is and how it reached us.

MIT's own files

lmdoc/cadr.164
AI Memo 528, CADR, MIT Artificial Intelligence Laboratory, in the printing of 15 May 1980. The machine described in MIT's own words, and the source for the data paths, the microinstruction classes, the clock, error checking, self bootstrapping and the diagnostic interface.
cadr/ir.bits
MIT's microinstruction field diagram, with the functional source and destination tables and the ALU and jump condition codes.
cadr/busint.erface
"Interface to the Bus Interface". The five cables, the signals on them, the diagnostic bus, and what WAIT and HANG mean.
cadr1/xspec.text.3
MIT's Xbus specification: the read and write cycles, the deskew delays, the arbitration, and the pinout of every kind of slot in the cage.
cadr1/dubspc.wires
MIT's wiring list for the double nine-slot backplane: the Unibus strips pin by pin, and the grant chains from slot to slot.
cadrwd/cadr4.wlr, cadrwd/icmem3.wlr, cadr1/busint.wlr
The wire lists the processor's two boards and the bus interface were wrapped from, wire by wire. The light panel's connector and the cable pairings are read from the first two.
cadr/cadr.book, cadr/icmem.book
The two print sets, which are what say which drawing belongs to which of the processor's two boards.
cadrtv/lmtv.order
MIT's programming specification for the display board: the frame buffer, the control words and the mode register.
cadrio/, cadrdc/, cadrm/, chaos/lispm/
The drawings of the I/O board, the disk controller, the memory board and the Chaosnet interface, each with its own wire list, stuffing list and engineering change orders beside it.
sys/ucadr/promh.text
MIT's source for the boot PROM, with its comments. The account of the boot sequence above is this file.
sys/ubin/promh.mcr, sys/ubin/ucadr.mcr
The boot PROM as the machine runs it, and microcode 323 itself.

sys/doc/disk.text

sys/io1/serial.lisp, sys/io1/time.lisp

sys/ucadr/uc-cadr.lisp, uc-interrupt.lisp, uc-disk.lisp, uc-cold-disk.lisp
The microcode that reads the I/O board, takes its interrupts, and builds the disk controller's command lists.
