# The mutation list: bugs the checks have to catch.
#
# Every record below breaks the fabric in one specific way.  `make mutants`
# applies each to a copy of rtl/ and tb/, rebuilds, and runs the check that is
# supposed to notice.  A mutation the check catches is a check doing its job.
# One that survives is a hole, and it stays in the list until the check is
# fixed --- it is never quietly dropped.
#
# WHERE THE LIST CAME FROM.  CLAUDE.md's "What went wrong, and what caught it"
# records eight bugs, every one of which passed something before it was found.
# Those are the seed, because a check that would not catch a bug that was
# really made is not a check.  In order, and by the name each has here:
#
#   -MEMACK on a write is combinational
#       memack-registered-on-a-write
#   a request standing at the master clock edge is granted at that edge
#       grant-waits-for-a-later-edge
#   the timeout oscillator free-runs from power-on
#       timeout-oscillator-restarted-at-the-grant
#   a shadow memory must come from the stimulus, never the DUT
#       bridge-writes-the-address-instead-of-the-data
#       bridge-drops-an-address-bit
#   reads and writes must be able to meet
#       NOT HERE.  That one is in the stimulus generator rather than in the
#       fabric --- golden/src/busint_xbus.rs asserts the coprimality --- and a
#       mutation of it needs golden/ copied and rebuilt per mutation.  Issue
#       #6.  So the claim holds for seven of the eight, not eight.
#   a slave that only records the address cannot see a duplicate handshake
#       awvalid-held-up-after-awready
#   a stimulus more polite than the real consumer tests less
#       master-returns-to-idle-early
#   mutation runners must not hide build failures
#       NOT A MUTATION.  It is a property of the runner, and run.py holds it:
#       nothing reuses a build directory, and a build that fails is reported
#       as BROKEN and exits non-zero rather than counting as anything.
#
# The rest of the list is not a regression suite for those.  It walks the
# constants, the boundaries and the handshakes of each check in turn, because
# the question is whether the check covers its module, not whether it covers
# eight remembered afternoons.
#
# LINT MUST NOT DO THE CATCHING.  Verilator runs -Wall with warnings fatal, so
# a mutation that leaves a signal or even a *bit* of a signal unread fails to
# build and the check never sees it.  That is why several records below are
# written to keep every bit used --- the address mixed into the word rather
# than replacing it, a constant moved rather than a term deleted.  Where the
# obvious way to write a bug would be rejected by lint, the note says so.
#
# THE FORMAT.  Records are literal text, not patches: no line numbers and no
# context, so a record rots only when the lines it actually names change.
# `@old` must match its file exactly once or the run fails.  Every line
# between `@old`, `@new` and `@end` is source, verbatim, including its
# leading whitespace.
#
#   @mutation  a kebab-case name; how a survivor is reported
#   @check     which check has to catch it; `run.py`'s CHECKS is the list
#   @file      which file to mutate; the check must build it
#   @hole      optional: the issue holding a known hole open, as `@hole #3`
#   @note      prose, repeatable; printed when the mutation survives
#   @old       the source to replace, exactly as it stands
#   @new       what to put there; empty deletes
#   @end
#
# A slice gets mutations when it lands, and not before.  `microcycle` was
# deliberately absent while stage 4 was being written, on the grounds that a
# record against a file still moving rots before it is read; it has records
# now because the slices landed.  The same will be true of whatever comes
# after it.
#
# WHAT IS KNOWINGLY NOT CAUGHT.  Some records below carry `@hole`, which names
# the issue that holds the hole open.  They are reported every run, counted in
# their own column, and do not fail it.  How many there are is the run's answer
# and is deliberately not written here: a count in prose is a thing that goes
# stale the first time somebody closes one.
#
# A CLOSED ISSUE MEANS THE RECORD NEEDS REVISITING, and nothing here can
# tell you that. The inverse check fires when a hole *closes* --- the
# mutation becomes caught and the run fails, naming the issue and the line.
# It cannot fire when the ISSUE closes while the mutation still survives,
# which is what happens when a survivor turns out to be an equivalence: the
# question is answered, the `@hole` is now a suppression of nothing, and the
# run stays green. It happened once, to #5. So when an issue named here is
# closed, come back to its record: either the mutation is caught now, or it
# never could be and belongs rewritten with the reasoning, as #5's is.
#
# NOT EVERY `@hole` IS A DEBT. Some are predictions, and one of them has
# already come true. #9's two records were held open by the composed check
# stopping at a wall --- about five hundred bus cycles at the very end of the
# boot PROM, too few reads for the mutation to reach a compared column --- and
# the note said they should begin failing ON THEIR OWN when that wall moved.
# It moved; the run reported CLOSED, named the issue and the line, and the
# records are live now with nothing changed in them. That is the argument for
# the inverse check in one paragraph: a comment saying "revisit when X" trusts
# somebody to remember, and this enforced the revisit instead.
#
# #1's two records are the same kind of prediction and are still open: two of
# the three terms of -WAIT that no observed program fires. They are not
# defects, and the day a program exercises the stall path they will say so.
#
# `@hole` is not a way to make a survivor go away, and three things stop it
# from becoming one.
#
# It takes an issue number, so a hole cannot be recorded without being
# written down somewhere a person will see it.
#
# The record stays in the list, mutating exactly what it did before.  A
# survivor that is quietly deleted is a check that silently got weaker, and
# nothing afterwards would show it.
#
# And a mutation that is CAUGHT while still carrying an `@hole` fails the run
# --- the hole has closed and the record has not caught up.  That is the
# inverse check, and it is the part that keeps the field safe to have: without
# it the list would accumulate `@hole`s for holes that shut long ago.
#
# The reason to have it at all is that a target red by design cannot report a
# fifth survivor: red for four known reasons looks exactly like red for five.
# A recorded exception with a reason is this repository's existing idiom ---
# CLAUDE.md's "Where the fabric parts from muir", and the testbench not
# comparing -TPR60 while RESET is high. An unrecorded one is what nothing here
# tolerates.

#
# ------------------------------------------------------------------------
# HOW A RECORD GOES STALE, AND IN WHICH DIRECTION
#
# The literal text rots LOUDLY and the reasoning rots SILENTLY.  That
# asymmetry is the whole of what to watch.  Four directions, three noisy:
#
#   THE `@old` STOPS MATCHING.  The file moved under the record --- a rename,
#   a reindent, a line that grew a comment.  UNAPPLIED, and the run fails
#   naming the record and the file.
#
#   THE `@old` MATCHES TWICE.  A line was duplicated, and a record that could
#   mutate either one tests whichever the parser reached first.  Exactly once
#   or the run fails; that rule exists for this.
#
#   THE `@new` NAMES SOMETHING THAT HAS GONE.  The mutant does not build:
#   BROKEN, which is never a verdict on the check and always one on the
#   record.
#
#   AND THE SILENT ONE --- A WHOLE CHECK, OR A WHOLE FILE, WITH NOTHING AIMED
#   AT IT.  Nothing about this is ever wrong.  The run is green, every count
#   is right, and a module is untested.  Two guards exist because nothing else
#   would ever say so: `check_coverage` names a file a check builds that no
#   record touches, and `check_makefile` reads the Makefile in BOTH
#   directions --- "the Makefile runs a check this runner has never heard of"
#   being the direction that hides.  `machine` was exactly that for a while.
#
# The `@note`s are prose and nothing checks them.  When a note names a number,
# a microcycle, a file or an issue, that is the part of the record most likely
# to be false, and it fails no run when it is.  #5's `@hole` outlived the
# issue that justified it and every run stayed green.
#
# ------------------------------------------------------------------------
# WHEN A MUTATION SURVIVES: SIX THAT COULD NOT HAVE DONE ANYTHING ELSE
#
# A survivor is a finding, never something to tune away.  But the first
# question is not "which check is weak".  Six records here document mutations
# nothing can catch, and every one has the same shape: THE MUTATION PRESERVED
# AN INVARIANT THE CHECK DEPENDS ON.  Not a gap in the check --- something
# upstream holding still, which makes the change unobservable.
#
#   the timer's edge test, dropped      a rise not counted puts the next rise
#                                       a full period on: the same instant
#                                       the fall in between would give
#   the bridge latching on a write      the gate that stops a write strobing
#     (filed as hole #5 first)          MD is the processor's, not the
#                                       bridge's
#   the scratchpad compare, all ten     `wadr[9:5]` is zero on every cycle
#     bits instead of five              `destmd` is set
#   registering the map's first level   its address is a microcycle register,
#                                       so it is constant for the cycle
#   crossing -MEMACK and -LOADMD        `cadr_busint_xbus.sv` assigns the same
#                                       expression to both
#   rotating the device write word      all 5,650 device writes the boot PROM
#                                       makes carry zero, and a bijection on
#                                       zero is zero
#
# So when something survives, ask WHAT IS CONSTANT HERE THAT I DID NOT NOTICE.
# And notice which kind of constant it is: three of the six are constants of
# the WORKLOAD and not of the design --- the all-zero device word, the boot
# PROM's traffic, an address that only holds still because both its sources
# are microcycle registers.  Those stop being true the day the workload
# changes, so the device-word record's check counts distinct words and says so
# when the count rises above one.  The note goes wrong on its own and the run
# announces it, rather than waiting for somebody to remember.
#
# SWEEP THE MAGNITUDE; DO NOT ASK A YES/NO QUESTION.  Delaying the map by one
# tick survives, and so do 4 and 16; 28 is caught on PCS0 at microcycle
# 2,084,731 and 44 on JCOND at 1,062,763.  The answer worth having was not
# "caught" but WHERE THE EDGE IS --- the check is blind only below one
# microcycle, which is exactly where the staleness is not real.  A yes/no
# question would have recorded an equivalence and stopped there.
#
# Hence the rule: REPLACE AN EQUIVALENT MUTANT WITH THE SMALLEST MAGNITUDE
# THAT IS CAUGHT.  An equivalent mutant must be explained forever and tests
# nothing; a live one testing the same property costs the same line.
#
# ------------------------------------------------------------------------
# A CHECK THAT GOT WEAKER, AND `--since`
#
# A survivor and a regression look identical: nothing caught it, and the list
# either says why or does not.  `mutations/run.py --since <rev>` re-runs
# everything NOT CAUGHT NOW against that revision, archived, and reports which
# were caught there --- so "this used to be caught" is something the run
# states rather than something a person happens to notice.
#
# IT COVERS `@hole` RECORDS AS WELL AS SURVIVORS, and that is the point rather
# than an extra.  A recorded exception is exactly where a regression hides:
# the run is green, the record says "known", and nothing asks whether it was
# always known.  The one regression found this way, #12, was carried by a
# mutation that happened to have no `@hole` on it.  That was luck.  With one,
# the run would have stayed green and been confident about it.
#
# ------------------------------------------------------------------------
# THE PATH THAT ONLY EXISTS ONCE THE THING WORKS
#
# Not about mutations.  It is here because this is where the next person reads
# about checking things, and it is the sharpest lesson this project has had.
#
# A DIAGNOSTIC GETS LESS TESTING THAN THE THING IT DIAGNOSES, and its SUCCESS
# branch gets none at all while the thing is failing.  `boards/arty-z7-20/vivado/fit.tcl` and
# `boards/arty-z7-20/vivado/bitstream.tcl` both did `get_property SLACK [get_timing_paths ...]`
# unguarded.  That call returns an empty list when there is nothing to report,
# and nothing to report is what meeting timing looks like --- so the first
# design to close timing would have thrown, exited non-zero and printed
# nothing.  Success reading exactly like failure, on the run that proved it
# worked.
#
# One was found by running it.  The other was found by GREPPING FOR THE SAME
# EXPRESSION IN ITS SIBLING, thirty seconds after fixing the first, and it was
# fixed before the run that would have hit it arrived.  When a project has
# been failing at something for a long time, none of its success paths has
# ever executed.  So when you fix a bug in a diagnostic, look for the same
# shape next door instead of waiting for it to happen twice.

@mutation tse-falls-late
@check phase_gen
@file rtl/machine/cadr_phase_gen.sv
@note TPTSE goes away at 5 ns and comes back at 25. Moving the fall to 10
@note leaves the pulse the right shape and in the wrong place.
@old
  localparam int unsigned TSE_OFF_T  = 5 / TICK_NS;    //   5 ns
@new
  localparam int unsigned TSE_OFF_T  = 10 / TICK_NS;   //  10 ns
@end

@mutation tse-returns-late
@check phase_gen
@file rtl/machine/cadr_phase_gen.sv
@note The other end of the same pulse.
@old
  localparam int unsigned TSE_ON_T   = 25 / TICK_NS;   //  25 ns
@new
  localparam int unsigned TSE_ON_T   = 30 / TICK_NS;   //  30 ns
@end

@mutation tpr60-opens-early
@check phase_gen
@file rtl/machine/cadr_phase_gen.sv
@note -TPR60 is a window on the phase, 60 to 100 ns, and SPEEDCLK's source.
@note Opening it at 55 is five nanoseconds of a signal that drives the front
@note panel's clock.
@old
  localparam int unsigned TPR60_ON_T = 60 / TICK_NS;   //  60 ns
@new
  localparam int unsigned TPR60_ON_T = 55 / TICK_NS;   //  55 ns
@end

@mutation tpr60-closes-a-tick-late
@check phase_gen
@file rtl/machine/cadr_phase_gen.sv
@note The window is half-open in muir --- `(60..60+TPR_PULSE_NS)` --- so the
@note tick at 100 ns is outside it. An inclusive compare is the off-by-one
@note that a range written as two comparisons invites.
@old
  assign n_tpr60 = !(running && phase >= 6'(TPR60_ON_T) && phase < 6'(TPR60_OFF_T));
@new
  assign n_tpr60 = !(running && phase >= 6'(TPR60_ON_T) && phase <= 6'(TPR60_OFF_T));
@end

@mutation normal-speed-reads-the-fast-tap
@check phase_gen
@file rtl/machine/cadr_phase_gen.sv
@note The 74S151 at CLOCK1 1D08 selects the read phase on {SSPEED1, SSPEED0,
@note -ILONG}. One wrong entry in that table is one wrong microcycle length,
@note and the testbench's tap coverage exists for exactly this.
@old
      SPEED_NORMAL:     read_sel = ilong ? 6'd25 : 6'd17;  // 125 : 85 ns
@new
      SPEED_NORMAL:     read_sel = ilong ? 6'd23 : 6'd17;  // 115 : 85 ns
@end

@mutation extra-slow-stretches-with-ilong
@check phase_gen
@file rtl/machine/cadr_phase_gen.sv
@note At extra slow, 160 ns is already the longest tap the chain provides, so
@note ILONG adds nothing. Making it stretch anyway is the reading of "ILONG
@note adds forty nanoseconds" that forgets the exception.
@old
      SPEED_EXTRA_SLOW: read_sel = 6'd32;                  // 160 ns, both
@new
      SPEED_EXTRA_SLOW: read_sel = ilong ? 6'd40 : 6'd32;  // 200 : 160 ns
@end

@mutation the-read-phase-is-selected-at-the-start-of-the-cycle
@check phase_gen
@file rtl/machine/cadr_phase_gen.sv
@note The 74S151's output is read at 65 ns, not at the start of the cycle,
@note and it only shows if speed or ILONG move between the two --- which the
@note last segment of the trace does deliberately, "speed and ILONG changing
@note inside a cycle". Moved as a constant rather than by replacing the
@note compare with a literal, which would leave SELECT_T unused and let lint
@note catch it instead of the check.
@old
  localparam int unsigned SELECT_T   = 65 / TICK_NS;   //  65 ns
@new
  localparam int unsigned SELECT_T   = 5 / TICK_NS;    //   5 ns
@end

@mutation the-write-pulse-opens-a-tick-late
@check phase_gen
@file rtl/machine/cadr_phase_gen.sv
@note -TPW30, measured from the end of the read phase. The instant lives in
@note a register of its own since 5646c91, so that the counter drives a
@note comparator and nothing else; a tick out is a tick out either way.
@old
      if (phase == wp_on_at) n_tpwp <= 1'b0;
@new
      if (phase == wp_on_at + 6'd1) n_tpwp <= 1'b0;
@end

@mutation the-control-store-pulse-closes-late
@check phase_gen
@file rtl/machine/cadr_phase_gen.sv
@note -TPW45, the one that ends the write to the control store.
@old
  localparam int unsigned WPIRAM_OFF_T = 45 / TICK_NS; // -TPW45
@new

@mutation the-write-pulse-outlives-the-boundary
@check phase_gen
@file rtl/machine/cadr_phase_gen.sv
@note muir clamps the pulse to the cycle boundary --- `WP_OFF_NS.min(RESTART)`
@note --- because with no gate delays a pulse that outlived it would write at
@note the next instruction's address. Dropping the clamp is the bug that
@note comment is there to prevent.
@old
      if (wrap) n_tpwp <= 1'b1;
@new
@end

@mutation hang-restarts-the-cycle-instead-of-parking-it
@check phase_gen
@file rtl/machine/cadr_phase_gen.sv
@note -HANG holds the next -TPR0 off and the generator parks at cycle_t.
@note Written the other way round it parks when it should run and runs when
@note it should park. Inverted rather than deleted, because deleting the term
@note leaves `hang` unread and lint would catch it instead of the check.
@old
  assign phase_next = wrap ? (hang ? park_at : 6'd0) : phase + 6'd1;
@new
  assign phase_next = wrap ? (hang ? 6'd0 : park_at) : phase + 6'd1;
@end

@mutation the-parked-generator-never-wraps
@check phase_gen
@file rtl/machine/cadr_phase_gen.sv
@note `wrap` has two terms because the park is one tick past the last tick
@note of the cycle: without the second, a generator that -HANG parked would
@note count on past the end when -HANG lifted rather than starting a new
@note cycle. Since 5646c91 the two are separate registers, `wrap_at` and
@note `park_at`, which is a new way to get this wrong --- they can now drift
@note apart, where `cycle_t - 1` and `cycle_t` could not.
@old
  assign wrap       = (phase == wrap_at) || (phase == park_at);
@new
  assign wrap       = (phase == wrap_at);
@end


# ================================================================= cables ===
#
# Two targets hold this one, and it takes both. `cables.pass` is lint, which
# catches a direction or a name; `current` regenerates from muir and catches
# anything else, which is what CLAUDE.md means by "both netlists via
# part::pinout". The runner does the same to its copy.
#
# These are mutations of a *generated* file, so regenerate-and-diff catches
# them by construction. What that proves is that the committed copy cannot
# drift from muir unnoticed --- worth holding, since a checkout builds from
# the committed copy and not from the generator. The mutations with teeth are
# in golden/src/cables.rs, which is the only authority on the port list; those
# need golden/ rebuilt per mutation, and are issue #6 rather than records here.

@mutation a-wire-the-interface-drives-is-made-an-output
@check cables
@file rtl/machine/cadr_cables.svh
@note -MEMACK comes from the bus interface: the processor listens. Making it
@note an output is the direction error the whole generated header exists to
@note prevent, and it is the one kind lint alone can catch.
@old
    input  var logic n_MEMACK,    // -MEMACK
@new
    output var logic n_MEMACK,    // -MEMACK
@end

@mutation a-bidirectional-wire-loses-its-enable
@check cables
@file rtl/machine/cadr_cables.svh
@build-fails
@note Of the 92 wires, 48 are driven from both ends and are carried as value
@note plus enable out with the resolved wire back in, because fabric has no
@note bus to fight over. A wire that lost its enable would be driven always.
@old
    output var logic MEM31_oe,
@new
@end

@mutation a-signal-is-renamed
@check cables
@file rtl/machine/cadr_cables.svh
@build-fails
@note The mangling is settled and inherited by everything generated. A name
@note that drifted from it would still elaborate on its own; what says it has
@note drifted is that the generator writes something else.
@old
    output var logic n_MEMRQ,     // -MEMRQ
@new
    output var logic n_MEMREQ,    // -MEMRQ
@end

@mutation mits-name-for-a-wire-is-changed
@check cables
@file rtl/machine/cadr_cables.svh
@note The comment is MIT's own name, and cadr_cables.map is what ties every
@note identifier back to it. Lint cannot see a comment; only regenerating
@note can. This is the mutation that says `current` is load-bearing and not
@note ceremony.
@old
    output var logic WRCYC,       // WRCYC
@new
    output var logic WRCYC,       // WRCYCLE
@end


# ============================================================ busint, Xbus ===
#
# Held to muir's busint::Busint tick for tick. Three of the four bugs CLAUDE.md
# records against the bus interface are here; the fourth is in the bridge.

@mutation memack-registered-on-a-write
@check busint_xbus
@file rtl/machine/cadr_busint_xbus.sv
@note XACK is made from XBUS ACK IN by the 74S64 at REQLM 0C11 --- a gate.
@note Only a read goes through the 60 ns tap of the TD100 at 0C09. Registering
@note both puts the acknowledgement a tick late on every write.
@old
              || (state == GRANTED && ((write && answering) || deskewed))
@new
              || (state == GRANTED && ((write && answered) || deskewed))
@end

@mutation grant-waits-for-a-later-edge
@check busint_xbus
@file rtl/machine/cadr_busint_xbus.sv
@note A request standing at the master clock edge is granted at that edge:
@note the priority logic registers -MEMRQ and does not care how long it has
@note been up. Making it always wait for the next edge costs a whole
@note microcycle on any request that arrives on one.
@note
@note The block grew the Unibus branch after this was written, and then the
@note two held Unibus instants in place of `ssyn_at`; what the mutation does
@note is unchanged --- every request waits for a later edge, whichever bus it
@note is for. The anchor has to follow the block, which is the loud kind of
@note rot and the reason `@old` is a literal.
@old
            write <= wrcyc;
            if (mclk) begin
              elapsed     <= 10'd0;
              answered    <= 1'b0;
              answered_at <= 10'd0;
              ssyn_seen   <= 1'b0;
              ub_ack_at   <= 10'd0;
              ub_md_at    <= 10'd0;
              tmr_fell    <= 1'b0;
              tmr_rises   <= 3'd0;
              nxm         <= 1'b0;
              if (unibus) begin
                state <= ARB;
                stage <= ub_master ? 3'd4 : 3'd1;
              end else begin
                state <= GRANTED;
              end
            end else begin
              state <= REQUESTED;
            end
@new
            write <= wrcyc;
            state <= REQUESTED;
@end

@mutation timeout-oscillator-restarted-at-the-grant
@check busint_xbus
@file rtl/machine/cadr_busint_xbus.sv
@note The 74LS124 at REQTIM 0A01 has run since the power came up, and the
@note grant only opens its output. Restarting it at the grant is the obvious
@note way to write it and is wrong on every cycle but the lucky ones --- it
@note only shows because the trace's grants land at varied phases.
@old
    if (rst) begin
      vco_count <= 7'd0;
      vco       <= 1'b1;
@new
    if (rst || (mclk && !n_memrq && state != GRANTED && state != ACKED)) begin
      vco_count <= 7'd0;
      vco       <= 1'b1;
@end

@mutation xbus-rq-dropped-at-the-acknowledgement
@check busint_xbus
@file rtl/machine/cadr_busint_xbus.sv
@note "-XBUS.ACK ... remains asserted until the -XBUS.RQ signal is removed by
@note the master": the request stays out through the acknowledgement, and the
@note slave holds its answer against it. A master that dropped it the moment
@note the cycle was acknowledged would break every slave that obeys the
@note specification.
@old
  assign dev_rq    = (state == GRANTED && elapsed >= 10'(SETUP_T)) || state == ACKED;
@new
  assign dev_rq    = (state == GRANTED && elapsed >= 10'(SETUP_T));
@end

@mutation the-setup-time-is-short
@check busint_xbus
@file rtl/machine/cadr_busint_xbus.sv
@note "it is the responsibility of the bus master to assert good address,
@note write, and data lines 80 ns. prior to asserting -XBUS.RQ".
@note
@note AND IT NOW HOLDS A TIMING EXCEPTION HONEST AS WELL, which is worth
@note saying because nothing about the record shows it. `rtl/plumbing/xilinx7/cadr_machine.xdc`
@note gives `mem_addr`, `mem_wdata` and `mem_write` sixteen ticks to reach the
@note AXI adapter's registers --- on the strength of the same sentence quoted
@note above, and nothing else. An exemption too wide tests nothing and looks
@note exactly like one that is right, and the only way to test its tightness
@note is a mutation of the DESIGN just outside the bound: a constraint cannot
@note be mutated from here, and trying would ask a two-level question.
@note Fifteen ticks where the exception claims sixteen is exactly one tick
@note outside it, which is what this already was.
@note
@note So this record did not change when the exception arrived --- the
@note exception arrived beside this note, in one commit --- and that is the
@note point: the check that catches a fabric that stopped honouring the 80 ns
@note is the same check that would catch a constraint claiming it wrongly.

# ============================================================ memory path ===
#
# Three checks at once: the timing still agrees with muir through the whole
# path, a read returns the word an earlier write put there, and a cycle
# nothing answered leaves MEM<31:0> at zero. The last two are held to the
# stimulus and not to anything the DUT produced, which is what
# `bridge-writes-the-address-instead-of-the-data` and
# `bridge-drops-an-address-bit` are here to prove.
#
# THE THIRD ARRIVED FROM ANOTHER CHECK. `the-bridge-holds-the-word-past-its-
# cycle` was a `ddr_boot` record until the full mutation run at `3743cf7`
# found it surviving: the property it holds was being exercised by the boot
# PROM's unanswered disk polls, and those stopped being unanswered at
# `70169fb`. It is here because this check's stimulus carries 29 cycles that
# nothing answers whatever any program does, and the testbench now fails if it
# ever stops carrying them.
#
# AND THE OTHER THING THAT SECTION SAYS `ddr_boot` CANNOT SEE, THIS CHECK CAN.
# The boot PROM's parity loop is an identity copy, so a bridge that wrote the
# word it had just READ is invisible there --- in that program the two words
# are the same. Here the word on the memory port is compared against the
# STIMULUS at the instant of the write and not through a read-back, so any
# wrong word is wrong whatever it is equal to. Measured at `3743cf7` with a
# two-hunk bridge that keeps its read word across cycles and writes it back:
# `ddr_boot` PASSES it outright --- 512 transactions, A and B differing only in
# word 255's bit 0, PC 544 still running --- and `memory_path` fails on the
# first write of the run,
#
#   tick 173: the word on the memory port is 936072919, reference says
#   1714741574
#
# 936072919 being the poison at physical 1, which the previous cycle read. It
# is not a record because it takes two hunks and a record takes one; the
# evidence is the measurement.

@mutation the-bridge-holds-the-word-past-its-cycle
@check memory_path
@file rtl/plumbing/cadr_xbus_ddr.sv
@note METE'S DECISION, HELD: an unanswered read gives MD zero.  `rdata` is
@note the slave's driver onto MEM<31:0>; held across cycles it hands MD a word
@note on every cycle nothing answered, because `cadr_memory_path.sv` falls
@note through to `memory_rdata` and -LOADMD is asserted on the NXM timer's
@note acknowledgement too.  On the DDR board that word is the last word of
@note page 0 and bit 0 of it is what the boot PROM reads as a ready disk
@note controller, so what happened to be in main memory decided where the
@note machine went.
@note
@note **THIS RECORD IS WHY `--since` EXISTS, met live.**  It was aimed at
@note `ddr_boot` and caught by configuration B from `05d28fa`; at `70169fb`
@note the disk controller's registers began answering the boot PROM's 16,951
@note polls, which were the unanswered cycles the mutation needed, and it
@note SURVIVED from there.  `make mutants` was red at HEAD for three commits
@note while every `make check` was green, and nothing but the full run could
@note see it: the property was held by which program happened to be running.
@note A check aimed at a program's incidental behaviour has a shelf life.
@note
@note IT IS AIMED AT THE STIMULUS NOW.  `tb/cadr_memory_path_tb.cpp` asserts
@note the rule directly --- at the acknowledgement of every cycle nothing
@note answered, MEM<31:0> must read zero --- on the 20 unanswered reads and 9
@note unanswered writes `build/busint_xbus.golden` already carries, and the
@note testbench fails the run if the stimulus ever stops carrying them.  The
@note line that fires first is
@note
@note   tick 1360: MEM<31:0> on a cycle nothing answered is 1803043649,
@note   reference says 0
@note
@note and the run stops at its bound of 20 of them.  1803043649 is the model's
@note poison at physical 3, which is the last address the trace read before
@note that cycle --- the word the bridge should have let go of when its own
@note cycle ended.
@note
@note MEASURED WHERE IT IS NOT CAUGHT, so that nobody re-aims it hopefully:
@note it survives `machine`, `probe` and, since `70169fb`, `ddr_boot`.  None
@note of those leaves a word in this register and then runs a cycle nothing
@note answers whose data anything looks at.  Measured at `05d28fa` for
@note `machine` and `probe`, and at `3743cf7` for `ddr_boot`.
@old
      done  <= 1'b0;
      rdata <= 32'd0;
    end else if (mem_done && !done) begin
@new
      done  <= 1'b0;
    end else if (mem_done && !done) begin
@end

# ============================================================ the widening ===
#
# `rtl/plumbing/cadr_axi_widen.sv`: the machine's 32-bit word in `S_AXI_HP0`'s 64-bit
# beat.  Six assignments, and until they were pulled out into a module they
# lived in `boards/arty-z7-20/cadr_arty.sv`'s `g_ddr`, where nothing could reach them --- the
# top level has an `MMCME2_BASE` and a `PS7` in it and Verilator has neither,
# so lint and the fitter were the whole of the evidence.  Every mutation below
# builds, lints, fits and programs; none of them is anything but a machine that
# reads back the wrong word.
#
# WHAT THE CHECK IS.  `tb/cadr_axi_widen_tb.cpp` applies the DUT's own `m_wdata`
# and `m_wstrb` into a model beat the *stimulus* chose the index of, and
# compares the whole beat --- both halves --- against a shadow the stimulus
# filled.  The memory is poisoned rather than zeroed, so a wrong lane always has
# a wrong answer to return, and the two channels are driven independently, so a
# lane selected from the wrong one of them shows.  The one thing that structure
# cannot catch is an address bug --- a model keyed by the DUT's address moves
# with it --- so the beat address is compared directly against what the
# stimulus address should have produced, over addresses whose every bit above
# the beat boundary takes both values.

@mutation the-read-lane-is-taken-from-the-wrong-half
@check axi_widen
@file rtl/plumbing/cadr_axi_widen.sv
@note The lane select inverted: a read of the low word gives the high one and
@note the other way about. Both halves stay read, so lint has nothing to say
@note about it, and on the board it is a machine whose every other main-memory
@note read is a different word.
@note
@note This is the mutation the poison exists for. Against a model memory of
@note zeros the first read of any beat returns zero whichever half it takes,
@note and it is only the second that could disagree.
@old
  assign s_rdata = s_araddr[2] ? m_rdata[63:32] : m_rdata[31:0];
@new
  assign s_rdata = s_araddr[2] ? m_rdata[31:0] : m_rdata[63:32];
@end

@mutation the-read-lane-is-selected-by-the-write-address
@check axi_widen
@file rtl/plumbing/cadr_axi_widen.sv
@note Each direction has to take its own address: the strobes are placed by
@note `s_awaddr` and the lane is selected by `s_araddr`, because those are the
@note addresses the two transactions are at. `cadr_axi_master` holds each
@note until the next transaction of that kind replaces it, so on a read
@note `awaddr` is some earlier write's address and agrees with `araddr` about
@note bit 2 half the time. A testbench that drove one address into both
@note channels would never see this.
@note
@note Written as an XOR rather than as a substitution: replacing `s_araddr[2]`
@note outright leaves it unread everywhere --- the beat address takes 31:3 ---
@note and Verilator would reject the mutation instead of the check catching it.
@old
  assign s_rdata = s_araddr[2] ? m_rdata[63:32] : m_rdata[31:0];
@new
  assign s_rdata = (s_araddr[2] ^ s_awaddr[2]) ? m_rdata[63:32] : m_rdata[31:0];
@end

@mutation the-write-reaches-both-halves-of-the-beat
@check axi_widen
@file rtl/plumbing/cadr_axi_widen.sv
@note The strobes are the whole of what keeps a write out of the half it is
@note not addressed to: the word is offered in both halves of the beat, so a
@note strobe pattern that opens both writes the neighbouring word as well.
@note Silent on the board --- every read of the addressed word is right, and
@note the word beside it is quietly destroyed.
@note
@note One arm only, so `s_awaddr[2]` stays read. The check catches it twice
@note over, once as a strobe pattern and once as the beat the write left
@note behind, and both messages are printed.
@old
  assign m_wstrb = s_awaddr[2] ? {s_wstrb, 4'b0000} : {4'b0000, s_wstrb};
@new
  assign m_wstrb = s_awaddr[2] ? {s_wstrb, s_wstrb} : {4'b0000, s_wstrb};
@end

@mutation the-half-selecting-bit-leaks-into-the-beat-address
@check axi_widen
@file rtl/plumbing/cadr_axi_widen.sv
@note The beat address is the word's with the low three bits cleared. Clearing
@note two of them leaves bit 2 in it, so the port is asked for a beat at a
@note four-byte boundary --- which on a 64-bit AXI3 port with `AWSIZE` of eight
@note is an unaligned transfer, and the strobes below have already accounted
@note for that bit. The word would land four bytes on.
@note
@note The only mutation here that the read-back property cannot catch, and the
@note reason the testbench compares the address directly: a model memory keyed
@note by the address the DUT presented would write consistent nonsense at the
@note wrong beat and read it back from the same wrong beat. CLAUDE.md's shadow
@note memory lesson, in the one place in this module where it applies.
@old
  assign m_awaddr = {s_awaddr[31:3], 3'b000};
@new
  assign m_awaddr = {s_awaddr[31:2], 2'b00};
@end

@mutation the-word-is-offered-in-only-one-half-of-the-beat
@check axi_widen
@file rtl/plumbing/cadr_axi_widen.sv
@note The word goes into both halves of the beat and the strobes choose which
@note copy lands. Offering it only in the low half makes every write to an odd
@note word write zero, and only that: the strobes are still right, so the
@note transaction is legal AXI and the port takes it without complaint.
@old
  assign m_wdata = {s_wdata, s_wdata};
@new
  assign m_wdata = {32'd0, s_wdata};
@end

@mutation the-beat-says-it-is-a-word-wide
@check axi_widen
@file rtl/plumbing/cadr_axi_widen.sv
@note `AWSIZE` and `ARSIZE` are the beat's and not the word's: eight bytes,
@note which is what makes a full-width beat with four strobes the way a
@note 32-bit word crosses a 64-bit port. Saying four bytes while driving
@note strobes in the upper half is a narrow transfer whose strobes are outside
@note the transfer, which is not legal AXI at all --- and which the adapter's
@note own `s_awsize` says, so this is exactly the mistake of deriving the
@note beat's size from the word's.
@old
  localparam logic [1:0] SIZE_BEAT = 2'b11;
@new
  localparam logic [1:0] SIZE_BEAT = 2'b10;

@mutation the-burst-length-the-port-takes-is-the-wrong-nibble
@check axi_widen
@file rtl/plumbing/cadr_axi_widen.sv
@note AXI4 carries eight bits of burst length and AXI3 four, so the narrowing
@note is a truncation. Rotating the nibble rather than taking another one,
@note because `s_arlen[7:4]` is already accounted for in the unused fold and
@note taking it here would leave `s_arlen[3:0]` unread --- lint would reject

@note
@note Both lengths are zero on every transaction the adapter makes, so this

@old

@new

# ============================================ the generators, on themselves ===
#
# Everything above mutates the fabric and asks whether a check notices. These
# two ask something else: whether the *generator's own assertions* are live.
#
# They are here because nothing downstream can stand in for them. `cables.rs`
# is the only authority on the port list --- regenerate-and-diff catches any
# edit to what it emits, but not an error in the emitting --- and
# `busint_xbus.rs` writes the stimulus and the expected outputs both, so a
# trace agreeing with itself proves nothing at all. In each the guard is an
# assertion inside the generator, and `make mutants` is the only thing that
# can ask whether it fires.
#
# The check for these is `cargo run`: the generator refusing to write is the
# mutation being caught. Build and run are separate, so a mutation rustc
# rejects is BROKEN and not caught.
#
# WHAT CANNOT BE MUTATED HERE, and it is worth saying rather than leaving as a
# gap someone else notices. Deleting an assertion is undetectable by running
# the program: an assertion that guards good input does nothing when the input
# is good, so removing it changes no output. What can be tested is whether the
# assertion catches a *wrong derivation* or a *wrong table*, which is what
# these do. An assertion nothing below trips is one nothing here can vouch for.

@mutation the-prose-table-disagrees-with-the-netlists
@check cables_gen
@file golden/src/cables.rs
@note cable.rs's own table names nine signals and says which end drives each.
@note cables.rs reproduces it and stops if the netlists disagree, because
@note where the prose and the netlists part one of them is wrong. -MEMACK
@note comes from the bus interface and the processor listens; saying the cpu
@note drives it too is the disagreement that has to stop the run.
@old
        ("-MEMACK", false, true),
@new
        ("-MEMACK", true, true),
@end

@mutation a-totem-pole-output-is-not-counted-as-a-driver

@note The direction of every one of the 92 wires comes from `part::pinout`
@note and `drive_of`: a wire with no driver on a side is one that side only
@note listens to. Dropping the plain totem-pole case makes drivers into
@note listeners wholesale --- the derivation wrong rather than the table ---
@note and the nine-signal cross-check is what has to notice.
@old
                Some(Drive::Totem) => any = true,
@new
                Some(Drive::Totem) => {}
@end

@mutation a-pull-up-is-counted-as-a-driver

@mutation the-cycle-timer-wraps-under-a-long-request

# ========================================================== the processor ===
#
# Two checks, one module: `microcycle` runs MIT's boot PROM and
# `microcycle_sys` a System 100 band. A mutation goes to the cheaper one
# unless the band is the only thing that reaches what it breaks --- the map,
# the dispatch memory's read, Q's shifter, the stack RAM, SINTR and -ILONG,
# which the boot PROM never touches. 600,000 microcycles against 2,200,000,
# and 84 MB against 297.
#
# NOT HERE YET: anything in the stall path, or touching `md`, `MBUSY` or
# `-LOADMD`. The processor is being composed with the memory path --- `md`
# stops being a trace column and comes from the real bus interface --- and
# mutations written against a design about to move are work done twice. That
# is where the tolerances live too: the sub-tick slip on stalled microcycles,
# the Unibus arbitration exemption, and the USE.MD discrimination.

@mutation the-a-memory-pass-around-is-inverted
@check microcycle
@file rtl/machine/cadr_microcycle.sv
@note A scratchpad write is one microcycle behind the instruction that
@note computed it, and the pass-around is what hides that from the microcode:
@note the comparators at ACTL 3B21/3B27 match the source address against the
@note pending WADR and put L on the bus instead of the memory's output. Taken
@note the wrong way round it reads the stale word exactly when it must not,
@note and the fresh one only when the memory already had it.
@old
  assign a = apass ? l : amem_q;
@new
  assign a = apass ? amem_q : l;
@end

@mutation the-a-memory-pass-around-never-fires
@check microcycle
@file rtl/machine/cadr_microcycle.sv
@note The comparator inverted rather than the mux: the pass-around fires on
@note every address but the one it is for. Inverted rather than deleted so
@note that `aadr` stays read.
@old
  assign apass = destd && (wadr == aadr);
@new
  assign apass = destd && (wadr != aadr);
@end

@mutation the-m-memory-pass-around-ignores-what-the-write-was
@check microcycle
@file rtl/machine/cadr_microcycle.sv
@note The 93S46 at MCTL 4B18 matches five bits of the pending write address
@note and `DESTMD` as its sixth. Without that sixth bit an A-only write
@note passes its word around to an M source whose address happens to match
@note the low five bits, and the microcode reads a word that was never
@note written where it is reading.
@note
@note Worth not re-deriving: the *other* obvious mutation here --- comparing
@note all ten bits, `wadr == {5'd0, madr}` --- is EQUIVALENT and not a
@note mutation at all. `destmd` and `wadr` are registered at the same edge
@note from the same instruction, and `wadr_in` is `{5'd0, ir[18:14]}`
@note whenever `destm`, so `wadr[9:5]` is zero on every cycle `destmd` is
@note set. It survives both processor checks because there is nothing to
@note catch.
@old
  assign mpass = destmd && (wadr[4:0] == madr);
@new
  assign mpass = (wadr[4:0] == madr);
@end

@mutation the-dispatch-mask-is-a-bit-too-wide
@check microcycle_sys
@file rtl/machine/cadr_microcycle.sv
@note `IR<7:5>` is a length and the mask is `(1 << len) - 1`. Without the
@note minus one every dispatch takes one more bit of R than it asked for.
@note On the band, because the boot PROM writes the dispatch memory
@note 2,048 times and reads it never: a wrong address there is a wrong
@note place to write and no one ever looks. Confirmed --- it survives
@note `microcycle` and is caught by `microcycle_sys`.
@old
  assign dmask  = (8'd1 << ir[7:5]) - 8'd1;
@new
  assign dmask  = (8'd1 << ir[7:5]);
@end

@mutation a-map-dispatch-is-recognised-by-the-wrong-gate
@check microcycle_sys
@file rtl/machine/cadr_microcycle.sv
@note `-DMAPBENB = NOR(IR8, IR9)` at DSPCTL 3F14, so a dispatch takes a map
@note bit *instead of* R0 whenever either bit is set. Read as a NAND it takes
@note the map bit only when both are, and R0 comes back in the rest of the
@note time --- which is the "easy misreading" the source names, arrived at
@note through the gate rather than through the OR.
@note Same routing and the same reason: no dispatch is ever read out of
@note the boot PROM's 2,048 writes. Survives `microcycle`, caught by
@note `microcycle_sys`.
@old
  assign dmap   = ir[8] || ir[9];
@new
  assign dmap   = ir[8] && ir[9];
@end

@mutation the-second-map-level-is-read-at-the-wrong-entry
@check microcycle_sys
@file rtl/machine/cadr_microcycle.sv
@note Both levels are asynchronous and chained combinationally: a lookup is
@note a ripple through two RAMs inside one cycle, the first level's five bits

@note entry off and every translation is plausible and wrong.
@note
@note WHY THE READ AND NOT `adr1` ITSELF, which is the mutation to reach for:
@note `adr1` addresses the write as well as the read. Change it and the map
@note is permuted consistently --- written to the wrong entry, read from the
@note same wrong entry --- and since a rotation is a bijection the mapping
@note from `MAPI` to `VMO` is untouched. It is a relabelling of the storage

@note word differs on 1,649,965 of 4,400,000 lookups and the permission bits

@note was self-consistent, not because the check was blind. A memory's

@mutation the-scratchpad-latches-follow-in-the-wrong-phase
@check microcycle_sys
@file rtl/machine/cadr_microcycle.sv
@note The third of the three things `rtl.rs`'s header calls easy to model one

@note is the 74S373 at ALATCH, MLATCH, PLATCH or SPCLCH, which follows the

@note one state too soon." Following in the write phase instead is that

@note write pulses now land while the latches are still following, which is

@note thousand microcycles of a program that loads the control
@note store leave the scratchpads reading the same few words

@mutation the-stacks-push-pass-around-is-inverted

@mutation the-first-map-level-is-read-a-microcycle-stale
@check microcycle_sys
@file rtl/machine/cadr_microcycle.sv
@note "THERE IS NO MMU STATE." Both levels are asynchronous and chained
@note combinationally --- VMEM0 1C14 drives `-VMAP4..0`, which are VMEM1
@note 1E04's address --- so a lookup is a ripple through two RAMs inside one
@note cycle. Delaying the first level by twenty-eight ticks is a microcycle
@note of staleness: the lookup belongs to the cycle before the one using it.
@note
@note WHY TWENTY-EIGHT AND NOT ONE, which is the mutation to reach for.
@note Registering the read --- one tick --- is EQUIVALENT, and so is any
@note delay below a microcycle. `MAPI` is `VMA<23:8>` or `MD<23:8>`, both
@note microcycle registers, so the level-1 address is constant for the whole
@note microcycle; a synchronous read of a constant address gives the same
@note word at every sampling point more than a tick after it settles, and
@note the read phase is 29 ticks at normal speed and 44 at extra slow.
@note
@note Found by sweeping the delay rather than asking whether one delay is
@note caught: 1, 4 and 16 ticks survive; 28 is caught on PCS0 at microcycle
@note 2,084,731 and 44 on JCOND at 1,062,763. So the check is blind only
@note *below one microcycle*, which is precisely where staleness is not real.
@note An equivalent mutant that must be explained forever is worth less than
@note a live one testing the same property, so the smallest magnitude that
@note is caught is what the list carries.
@note
@note WHAT THIS DOES NOT SAY, and it matters at bring-up: it does not say
@note the fabric may not register the map. Functionally it may --- that is
@note what the equivalence means. The lookup is combinational because
@note 2048 x 5 and 1024 x 24 fit in distributed RAM, which reads
@note asynchronously and costs nothing. If fit ever forced the map into
@note block RAM, THIS CHECK WOULD NOT OBJECT. That has to be decided from
@note the timing, not from here.
@old
  assign vmap = l1_map[adr0];
@new
  logic [4:0] vmap_d [0:27];
  always_ff @(posedge clk) begin
    vmap_d[0] <= l1_map[adr0];
    for (int d = 1; d < 28; d++) vmap_d[d] <= vmap_d[d-1];
  end
  assign vmap = vmap_d[27];
@end

@mutation the-map-is-written-with-the-wrong-frame

# ============================== MD holds what its instruction put there ===
#
# `md_hold` is the property `tb/cadr_md_hold_tb.cpp` measures every tick over
# both programs: MD has two writers, and a word strobed by `-LOADMD` before
# the `cpu_edge` at which `DESTMDR` writes MD may not land after it.  The map
# is indexed by `MD<23:8>` whenever `MEMSTART` is down and `wmapd` is
# registered at the boundary, so an instruction that puts a virtual address in
# MD and writes the map through it needs MD to stand for several microcycles;
# a stale word committing inside that span writes a map entry nobody asked
# for, silently.
#
# `docs/md-hold.md` carries the measurement, and one thing worth knowing
# before writing another record here: the mutation the check was written for
# --- suppressing the clear only for a boundary that carries a `DESTMDR`,
# which is the defect written out as one term --- SURVIVES every check in this
# repository, because `md_pending` is never set at a `cpu_edge` on either
# program.  It is not in the list, having no issue and no `@hole` to stand on.

@mutation the-held-word-is-never-let-go
@check md_hold
@file rtl/machine/cadr_microcycle.sv
@note MD's two writers are one `always_ff`: the held word committed at a
@note master clock edge or at once under `-HANG`, and `DESTMDR` at
@note `cpu_edge`.  `md_pending` is what says a word is still owed, and
@note clearing it at the commit is what stops the same word landing again.
@note Left set, every later master clock edge writes `md_held` over MD ---
@note including the boundary after an instruction has just put its own word
@note there, which is a word strobed before that instruction landing after
@note it.
@note
@note THAT IS THE SHAPE THE PROPERTY IS ABOUT.  The map is indexed by
@note `MD<23:8>` whenever `MEMSTART` is down and `wmapd` is registered at
@note the boundary, so an instruction that puts a virtual address in MD and
@note writes the map through it needs MD to stand for two to five
@note microcycles on the boot PROM and up to nineteen on the band.  A stale
@note word committing in there writes a map entry nobody asked for, and the
@note machine then reads through a translation of its own invention.
@note
@note Deleting the clear rather than negating a term, because that is the
@note whole of what the line does and every signal stays read either way.
@note
@note MEASURED AGAINST THE OTHER CHECKS RATHER THAN ASSUMED, as `map_boot`'s
@note records are: `md_hold` catches it at microcycle 536,303, the boot
@note PROM's first bus cycle, on the `md_pending` invariant, and `microcycle`
@note catches it too, at 537,844, on MD disagreeing with muir 1,541

@note other reports a wrong word somewhere downstream.
@old

@new

@end


# ================================================== the machine, composed ===
#
# The processor with the memory path under it and nothing driven nearer than

# ======================================================= the disk controller ===
#
# `rtl/machine/cadr_disk_controller.sv`, the four registers at 0o17377774, held to
# `disk_controller::Controller`'s `status()`, `read` and `write` over MIT's
# boot PROM.
#
# **READ THIS BEFORE FILING A HOLE HERE.  ON THIS TRACE THE WHOLE MODULE
# REDUCES TO ONE CONSTANT AND A DECODE, SO A MUTATION THAT LEAVES `0x2321`
# ALONE IS AN EQUIVALENCE AND NOT A HOLE.**  The boot PROM makes 11,301 reads
# of the status register, every one answering `0x2321`, and 5,650 writes of
# ZERO to the disk address register.  It never writes a command, never touches

# ================================================== the machine, behind DDR ===
#
# `build/ddr_boot.pass` runs the same eight modules as the composed check
# against a different question.  `machine` asks whether the fabric agrees with
# muir; this asks what it does where muir cannot follow.  muir has a modelled
# disk controller that answers the boot PROM's status polls and the board has
# `device_ack` tied low and none at all, so past about microcycle 537,900 the
# two machines part company by design.  What stands in for a reference is the
# boot PROM's own PAGE-0-PARITY-FIX --- 512 bus cycles, a read and a write of
# each of physical 0..377, the write carrying the word the read returned ---
# poisoned from outside, injectively in the address, against a modelled DDR3
# that answers at a delay that varies per transaction.
#
# WHAT THIS CHECK CAN AND CANNOT SEE ABOUT A WRITE, said here once so that
# nobody files the gap twice.  The parity loop is an IDENTITY copy: every
# write carries the word already at that address.  So a bridge that wrote the
# wrong word is caught only when the wrong word is DISTINGUISHABLE from the
# right one --- the address mixed in, the halves swapped --- and a bridge that
# wrote the word it had just READ is not caught at all, because in this
# program they are the same word.  That is an equivalence on this program, not
# a hole, and it is the control store's all-zero pass one bus along.  A
# configuration that once broke it existed: with an unanswered read handing MD
# the bridge's stale word, a poison with bit 0 set in word 255 made the PROM
# write a CCW to physical 777.  **That behaviour was decided against** --- an
# unanswered read gives MD zero --- and configuration B of the testbench is
# now what asserts it never happens.  The witness went with it; the write path
# stands on step two of the board plan, which proved it on silicon.
#
# AND THE RECORD THAT HELD THAT DECISION IS NO LONGER HERE.  `the-bridge-
# holds-the-word-past-its-cycle` was aimed at this check and caught by
# configuration B from `05d28fa`; at `70169fb` `rtl/machine/cadr_disk_controller.sv`
# began answering the boot PROM's 16,951 polls, which were the unanswered
# cycles it needed, and it survived from there.  It is a `memory_path` record
# now, where the stimulus carries unanswered cycles by construction rather
# than by what a program happens to do.  What configuration B asserts is
# unchanged and worth keeping --- page 0's contents must not steer the machine
# --- but it is no longer the thing holding the rule, and it can no longer BE
# that thing: the two unanswered cycles left on this program go to empty Xbus
# space and the PROM ignores what they return.

# ================================================ the memory port's tally ===
#
# `rtl/plumbing/cadr_mem_count.sv` is the board's only POSITIVE witness that the
# machine's memory cycles were answered, and everything below is aimed at it.
# The boot PROM's whole main-memory traffic is an identity copy of page 0, so
# page 0 reading back unchanged afterwards says the same thing whether the
# port answered or was never brought up; no lamp separates them either ---
# measured, LD2 reads the same with DDR and without, because the 16,951 disk
# polls time out either way. So step four of the board plan is read by four
# numbers on EMIO GPIO and by nothing else, which makes an unchecked
# instrument the worst kind of thing to have here: it will be read once and
# believed.
#
# `tb/cadr_mem_count_tb.cpp` runs the machine three times over the same
# adapter and widening the board has, and what each configuration is for
# decides which record below is caught by which:
#
#   LIVE   the port answers.  256 reads and 256 writes asked for, and 256 and
#          256 answered.  Anything that MIS-counts a handshake shows here.
#   DEAD   `hp0_aresetn` held low, which is a board before anybody has run
#          `ps7_post_config`.  The same 256 and 256 asked for, and NOTHING
#          answered.  Anything that counts the fabric's own intentions shows
#          here and only here.
#   HALF   the port takes a write and never answers it.  One read answered
#          and no writes --- the only reading in which the two directions
#          give different numbers, and so the only one that can see them
#          crossed.
#
# WHY THE THIRD CONFIGURATION EXISTS, since it is not a board anybody expects
# to meet: the boot PROM does exactly as many reads as writes, so a tally with
# its two directions crossed reads 256 and 256 in LIVE and 0 and 0 in DEAD and
# is invisible to both. `the-two-directions-of-the-tally-are-crossed` below is
# that mutation and HALF is what catches it. The configuration was written
# because the mutation survived, which is the order these things should
# happen in.
#
# WHAT CANNOT BE WRITTEN AS A RECORD HERE, so that nobody files a hole for it.
#
#   **A COUNTER OF `awvalid` INSTEAD OF `bvalid`.** The module is given the B
#   and R channels and nothing else of the port, so there is no request-side
#   port signal in it to count. That is the design and not an omission: the
#   two records that OR the machine's own request into an `answered` counter
#   are the same bug in the only form this module can express, and DEAD
#   catches them.
#
#   **DROPPING ONE TERM OF A HANDSHAKE** --- `bready` alone, `rready` alone,
#   `rlast` alone --- for two separate reasons, and it is worth keeping them
#   apart. Written the obvious way, by deleting the term, all three leave the
#   port unread and **Verilator does the catching**: `%Error: ... 'bready'
#   ... UNUSEDSIGNAL`, and the check never sees the mutation. Written so that
#   the signal stays read but is ignored --- `(bvalid && bready) || (bvalid
#   && !bready)` --- all three are EQUIVALENCES, measured: every number in
#   all three configurations is identical to a correct run's. That is not a
#   hole either. `cadr_axi_master` holds `bready` up from the tick it enters
#   WRESP, which is at least a tick before this slave can raise `bvalid`, so
#   `bvalid` is never asserted without `bready` beside it; the same argument
#   holds for `rready`; and at a burst of one every beat is the last, so
#   `rlast` never parts company with `rvalid`. The mutation that BITES is
#   dropping the slave's `valid` and counting the master's wait, which is
#   what the two `while-the-master-is-still-waiting` records below do.
#
#   **REMOVING THE SATURATION.** Nothing in this program reaches 32,767 of
#   anything, so a counter that wrapped would be identical here. The
#   saturation is for a machine that runs microcode, where a wrapped counter
#   reading a small number would be a false negative of exactly the kind this
#   module exists to rule out, and CLAUDE.md's `-XBUS.RQ` entry is the same
#   fact.
#
# AND THE PACKING IS MUTATED TOO, because it moved into this module from
# `boards/arty-z7-20/cadr_arty.sv` for the reason the widening did: a field placed one bit
# over in a file nothing can simulate is a number that still looks like a
# measurement. The two records that reach it are the marker bits and the two
# halves changing places.

# ================================================================ the witness ===
#
# `rtl/plumbing/cadr_prove.sv` is what goes on the board ahead of the machine, and it is
# the first thing here whose OTHER half is not fabric at all: a debugger
# reading and writing DDR from outside the design.  That is the whole reason
# the two steps exist --- CLAUDE.md's shadow-memory lesson says a model taken
# from the DUT moves with the bug, and an observer on the far side of the
# processing system cannot move at all --- and it is also why the check here
# has to bite.  A witness that is quietly wrong reports a memory fault that
# is its own.
#
# WHAT THE CHECK IS.  `tb/cadr_prove_tb.cpp` runs the harness --- the state
# machine with `cadr_axi_master` and `cadr_axi_widen` under it, wired as
# `boards/arty-z7-20/cadr_arty.sv`'s `g_ddr` wires them --- against a 64-bit AXI3 slave whose
# model memory is filled with the COMPLEMENT of the word before every
# transaction.  The beat address, the strobes and the strobed half of the data
# are each compared against what the stimulus asked for and never against what
# the DUT presented; the neighbour in the beat is required to be untouched; and
# the address sweeps bit 2 and every bit above the beat boundary.
#
# AND THE INPUTS GO BAD MID-TRANSACTION, which is the one thing the board can
# never test.  `addr`, `word` and `writes` are tied to constants there, so a
# witness that read them instead of its own registers would be right by
# accident for ever.  Here they are scribbled with the complement and the
# neighbouring lane the moment the payload is taken.
#
# WHAT NOTHING HERE CAN CATCH, and it is worth saying rather than filing.
# `boards/arty-z7-20/cadr_arty.sv` chooses the address and the word, and a top level that
# crossed `.addr(PROVE_ADDR)` with `.word(PROVE_WORD)` would leave every signal
# read, lint clean, and this check untouched --- the check cannot see the top
# level, and the top level cannot be simulated.  What stands against it is that
# both are localparams a person can read beside the reasoning for them, and
# that the debugger reads the address the file names.  It is the same limit
# `build/arty.pass` already has and not a new one.

@note `rtl/plumbing/xilinx7/cadr_ddr.xdc` relaxes the adapter's address and data registers to
@note sixteen ticks ON THE STRENGTH OF IT. So a witness that raises `mem_req`
@note early does not merely break a rule: it turns that constraint into a
@note claim about a board where it is false, and the fitter would time the
@note address path against 80 ns it does not have.
@note
@note Divided rather than replaced, so `SETUP_T` stays read and lint has

@note
@note THE COUNTDOWN IS LOADED IN TWO PLACES SINCE THE WRITE-BACK ARRIVED ---

# --------------------------------------------------- the probe, three of them
#
# `rtl/plumbing/xilinx7/cadr_probe.sv` is the instrument the board will be read through, and

# fails at microcycle 3 on `pc`, `ir`, `nop` and `lpc` --- 21 mismatches in

# -------------------------------------- the probe's reader, four of them
#
# `boards/arty-z7-20/vivado/probe.tcl` is the other half of the probe: the thing that reads the
# capture off the board over JTAG and writes what `tools/probe_check.py`
# diffs against muir. Everything above this line is fabric; these four are
# not, and they are here because a script nobody can run is the sharpest
# version of the problem this list exists for.
#
# IT SHIPPED WITH A ONE-CHARACTER BUG AND NOTHING COULD HAVE CAUGHT IT. The
# IDCODE scan drove TDI with zeros, so running off the end of the chain
# returned more zeros --- indistinguishable from bypass bits --- and 192 bits
# of padding were counted as 192 devices. The IR scans that followed were 778
# bits where the chain wants 10, an over-long IR scan keeps only its LAST
# bits, and those were the all-ones BYPASS padding: USER1 was never selected
# in anything and every sample read back as a bypass bit. It survived because
# exercising it took a board.
#
# The check is `tb/cadr_probe_jtag_tb.tcl` against `tb/cadr_jtag_chain.tcl`:
# seven chains, `tclsh`, no Vivado and no board, 80 ms. It asserts for each
# case the LINE the script must print and not merely its exit code --- which
# is what makes `the-instruction-register-is-measured-and-ignored` catchable
# at all. A name rather than a position: the list grows and `the third of
# these` would quietly come to mean something else.
#
# WHAT THE CHECK CANNOT SEE is in `tb/cadr_jtag_chain.tcl`'s header and is
# the thing to read before trusting a green run: it is a shift chain, not a
# TAP state machine and not silicon, so a DRCK edge, `BSCANE2`'s real
# behaviour and every property of `rtl/plumbing/xilinx7/cadr_probe.sv` are outside it. Those
# belong to the `probe` mutations above.
#
# THE REASONING BELOW WAS TRUE AT ace4131, which is where `boards/arty-z7-20/vivado/probe.tcl`
# reached its present shape and where the chain was measured on silicon: both
# IDCODEs exact, the part at the TDO end, IR total 10, first bit out least
# significant, DONE high. CLAUDE.md's rule is that `@old`/`@new` rots loudly
# and prose rots silently, so the commit is named rather than the reasoning
# left to read as true for ever.
#
# ONE THING IS NOT HERE. Restoring the IR-padding sweep the fix deleted is
# the obvious extra record and is not written: the sweep would find a
# working padding on every chain the model presents that has one, and pass.
# What the sweep really cost was the ability to say WHICH padding was right
# --- and that is what `the-instruction-register-is-measured-and-ignored`
# below tests directly, from the side the check can see.

# ================================ the disk controller, with a drive on it ===
#
# `rtl/machine/cadr_disk_controller.sv` again, and the other half of it.  The section
# above is what MIT's boot PROM can see --- one constant and a decode --- and
# these are what only a drive can: the eight unit slots, the spindle's block
# counter, the seek and its attention, the hang timer, and the two resets.
# The check is `build/disk.pass` against `golden/src/disk.rs`'s program, which
# reaches all sixteen command codes and every reachable status bit where the
# band reaches six codes and no error bit at all.
#
# **A MUTATION AIMED HERE COSTS A MINUTE**, because the trace holds one hang
# run out to `TIMEOUT_NS` and the fabric counts all 512,000,000 ticks of it.
# That is the price of a check that can tell that constant from a wrong one.
#
# **TWO EQUIVALENCES, BOTH MEASURED, SO THAT NOBODY FILES THEM AS HOLES.**
#
# muir's `reset_errors` clears the timeout flop only when the controller is
# NOT ACTIVE; the board clears it unconditionally on `-RESET ERR` and lets the
# running timer set it again at expiry.  This module takes the board's, and
# `if (not_active) timeout <= 1'b0;` in its place SURVIVES `disk`, `machine`,
# `ddr_boot` and `probe` --- measured, not reasoned.  It cannot be told apart:
# muir gates both `<11>` and the transfer lossage with not-active anyway, and
# the board's flop is not set until the timer has run out, which IS not-active.
# CLAUDE.md named it as a candidate before this slice was written.
#
# And `-RESET ERR` clearing BUSY as well as the error flops also survives, for
# a reason about the PROGRAM rather than about the structure: every store into
# the command register that the trace makes while the sequencer is hung
# carries code 0o16, which stops the channel and clears BUSY on purpose.  So
# the trace never asks whether a store that is NOT a reset leaves a hang
# running.  It is the control-store-writes-all-zeros shape once more --- the
# stimulus does not reach the distinction --- and the live record aimed at the
# same line is `disk-reset-err-reaches-the-drive`, which asks the other half
# of the question and is caught.
#
# WHAT THIS CHECK DELIBERATELY DOES NOT COVER, so that nobody files a hole
# against it: everything a transfer leaves behind.  This slice has no channel,
# so the last memory address, the ECC register, the eight channel status bits
# and the heads' position after a command list are exempt on the rows a
# data-moving command touches --- bounded and counted on the check's own
# output, which says how many rows each cost.  Records for those arrive with
# the channel.

# ----------------------------------------------------------------------------
# THE REQUEST PATH.  Twenty-four slots against 263,245 blocks cannot be
# pre-filled, so the walk that lacks a block posts its disk address, raises
# an interrupt and WAITS, and Linux fills a slot or denies it.  What follows
# holds each half of that: that the walk waits rather than missing, that it
# asks for the right block and stops asking when it arrives, that no status
# word lies while it waits, that it resumes within a stated number of ticks
# of the tag landing, that nothing moves while it waits, that the next block
# is asked for before the current one moves, that the unit is part of the
# tag, that the bookkeeping Linux reads is right, and that the interrupt
# follows its mask.  Every record is caught on its own line, named in its
# note.  The trace check holds the other half of the same design: with every
# block fetched before the START that needs it, no request is ever posted,
# and `disk-prefetch-asks-for-a-block-it-has` is the record that shows the
# trace sees that.

# ============================================== -XBUS.INTR, and its one gate ===
#
# The disk controller computes `interrupt()` and now DRIVES it, and
# `rtl/machine/cadr_machine.sv` ORs it with the display's where UBINTC 0E04 does.
# Until 2026-09-10 the level was computed and kept: `STATUS<3>` reported it,
# `cadr_machine`'s `sintr` was a stimulus port fed from the trace and
# `boards/arty-z7-20/cadr_arty.sv` tied it to zero.  What that cost was measured on the
# board that night --- the machine boots, loads its microcode off the pack,
# restores the whole band, and then spins for ever in `AWAIT-DISK` at
# microcode `0o25221`, because `A-DISK-BUSY` is cleared in exactly one place,
# `DISK-COMPLETION-OK`, reached only from the Xbus interrupt handler.
#
# WHERE EACH HALF IS HELD.  `disk` holds `Controller::interrupt()` and the
# port that carries it: `tb/cadr_disk_tb.cpp` compares -XBUS.INTR at the PORT
# against the trace's own `intr` column on every row, and the trace enables
# the done interrupt at row 260, the attention interrupt at row 264, raises
# the level on nine rows and reaches an ACTIVE controller with the done
# enable set at rows 320 and 321.  `machine` holds THE WIRE END TO END: the
# column is `Machine::xbus_interrupt()`, muir's own OR, and `sintr_o` is the
# fabric's, compared on all 600,000 microcycles of MIT's boot PROM.
#
# **THE COLUMN IS ZERO ON EVERY ONE OF THOSE ROWS, AND THAT IS WHY THE
# MACHINE-LEVEL RECORDS INVERT AN OPERAND RATHER THAN DROP IT.**  The boot
# PROM writes no command register and enables no display, so neither request
# is ever up at the machine's boundary --- while `not_active`, the interrupt's
# other term, is true throughout: 11,301 status polls all answer `0x2321`,
# `<0>` set.  So a fabric that ignored the enable, or that read either operand
# of the gate the wrong way round, raises the line and fails on the first row,
# and each of the two inversions below says that its own operand reaches the
# processor.
#
# WHAT NO CHECK HERE REACHES, MEASURED AND NOT FILED AS A HOLE.  Two things,
# and they fail differently.
#
# `disk_intr || tv_intr` with either operand DROPPED **does not build**: the
# dropped operand is read nowhere else in this module, so Verilator says
# `Signal is not used: 'tv_intr'` (or `'disk_intr'`) and the check never sees
# it.  Measured, both ways round.  That is the list's own rule about lint
# doing the catching, met here, and it is why the two records below invert an
# operand instead --- an inversion keeps every signal used and IS caught.
#
# `disk_intr && tv_intr`, the OR made an AND, **builds and SURVIVES**:
# `machine`, and `ddr_boot` and `probe` on the way past.  Both requests are
# down on every row of both reference programs, so `0 || 0` and `0 && 0` are
# the same zero --- and on the board it is the bug this slice exists to
# remove, one gate along, the disk unable to interrupt unless the display
# interrupts in the same tick.  Measured at this slice; not in the list,
# because a survivor is not a record and a record with an `@hole` needs an
# issue, and inventing one to hold a limit that was never a defect is the
# suppression this list exists to prevent.
#
# WHAT WOULD CLOSE IT is a machine-level reference whose program enables an
# interrupt.  **The band is not that reference**, and it is worth being exact
# about why: `rtl_sys.golden` has `sintr` up on 17,185 of its 2,200,000 rows
# and those really are the disk's done interrupt --- but `microcycle_sys` runs
# `cadr_microcycle` ALONE, where the disk is outside the module and `sintr` is
# properly a port with the trace driving it, so those rows check the
# PROCESSOR's end of the wire and can never reach this one.  A composed band
# check --- `cadr_machine` on `rtl_sys.golden` --- would need the pack side, a
# Linux serving blocks on demand, and something over a billion ticks; and
# muir's channel reaches main memory in no bus cycles at all where the
# fabric's takes the bus for 256 words a block, so the `ns` and `stall`
# columns would drift by the ten ticks `memory_path`'s configuration B
# measured and the rows could not be compared as they stand.  It is a slice,
# not a line.

# ---------------------------------------------------------------------------
# The I/O board: the keyboard, the mouse, the two clocks and the status
# register they share, on the Unibus.  `rtl/machine/cadr_io_board.sv` against
# `build/iob.golden`, which `golden/src/iob.rs` writes out of muir's own
# `ioboard::IoBoard` through `busint::IoBoardTiming`.
#
# THIS IS THE ONLY CHECK THAT CAN TELL THIS MODULE FROM A WIRE.  Measured with
# a probe against muir's `rtl` engine: MIT's boot PROM never addresses the card
# at all in 600,000 microcycles, and a System 100 band reaches three of its
# registers in 271 bus cycles of 141,849.  So every record aimed at the card
# carries `@check iob` and no other check sees any of them.
#
# WHAT CANNOT BE MUTATED HERE, said once so nobody hunts for it.  **muir's
# snap** --- `MouseInterface::sample` dragging a step whose due time has fallen
# behind the last edge forward onto that edge, so that the first two steps of a
# move land on consecutive `KB CLK^` edges and the rest on every other one ---
# is the MOUSE's behaviour and not the card's, and on this slice it lives in
# `tb/cadr_io_board_tb.cpp`.  A mutation cannot reach a testbench.  Slice one
# measured what getting it wrong costs (307 face rows and 27 read-backs, the
# counters one behind muir for the length of every move); the two records here
# that stand nearest it are `iob-the-mouse-samples-at-16-us` and
# `iob-the-mouse-clock-follows-the-microsecond-clocks-phase`, which break the
# card's half of the same agreement.
#
# AND ONE MEASURED EQUIVALENCE, so it is not filed as a hole: making
# `t_msyn`, `t_edge` or `edges` wrap rather than saturate survives, and not by
# luck --- `ub_ssyn` latches the first time `answer_now` is true and nothing
# clears it while `-UB MSYN` stands, so a wrapped counter still crosses its
# threshold for the first time at the same tick.  The module says so at the
# constant.

# THE I/O BOARD UNDER THE MACHINE: THE UNIBUS WITH BOTH ITS SLAVES
#
# `build/unibus.pass` against `cadr_memory_path` with the card instantiated
# inside it, which is slice three of the I/O board.  `iob` above is the card;
# this is the composition, and the two hold different things:
#
#   `iob`     the card alone, a Unibus master in the testbench, against muir's
#             `ioboard::IoBoard` through `busint::IoBoardTiming`.
#   `unibus`  a cycle of the MACHINE'S --- the bus interface arbitrating for
#             the Unibus, the address `cadr_memory_path` computed off the map,
#             the card's answer becoming -MEMACK and -LOADMD, and the word
#             reaching MEM<15:0>.
#
# **NO OTHER CHECK IN THIS REPOSITORY RUNS A UNIBUS READ.**  Measured:
# `build/machine.pass` prints "the Unibus arbitration of 1 of 17466 bus
# cycles", and that one cycle is MIT's boot PROM WRITING the mode register.
# `busint_xbus.golden`'s addresses are main memory and empty Xbus space and it
# runs no Unibus cycle at all.  So `cadr_busint_xbus.sv`'s MD strobe --- the
# one instant on either bus where the word and the acknowledgement come apart
# --- had never carried a word anybody compared, and the records below are the
# first thing that holds it.
#
# **AND THERE IS NO DECODE IN FRONT OF THE TWO SLAVES, WHICH IS WHAT MAKES
# THESE RECORDS LIVE.**  CLAUDE.md records the display's
# `tv-answers-its-neighbours` surviving because it honoured a guard that was
# exhaustively checked elsewhere: a mutation downstream of such a guard tests
# the guard and not the thing.  Here each slave matches the whole address for
# itself, as a board on the backplane does, so a match widened in either of
# them is visible --- and `ub_ssyn_by` says which slave pulled the line, so two
# answering at once is measured rather than inferred from the word that came
# back.

@mutation unibus-the-word-comes-from-the-other-slave
@check unibus
@file rtl/machine/cadr_memory_path.sv
@note **The mux on the returned word, crossed.**  Two slaves share
@note `-UB SSYN` the way the open-collector line on the backplane shares it,
@note and the word has to come from whichever of them is answering.  Crossed,
@note a read of the card gives back the diagnostic register block's word and a
@note read of the block gives back the card's.
@note
@note This is the mutation the check's poison exists for.  `spy_rdata` is
@note driven from the address `tb/cadr_unibus_tb.cpp` is itself driving ---
@note never from `spy_eadr`, which is the DUT's --- and is injective in the
@note register number, so a card read that comes back as the poison and a
@note block read that does not are both named at the word.

@note Both signals stay read, so lint does no catching here.

@new

@end

# THE MAP, WRITTEN AND THEN READ THROUGH, AGAINST A REAL MEMORY
#
# `map_boot` is `machine` with one thing changed: `mem_rdata` is fetched from a
# store keyed by `mem_addr` instead of handed over keyed by the trace's row, so
# the physical address the map produced is used to fetch something.  Page 0
# holds what muir's memory holds --- zero --- and every other address holds a
# poison injective in it, so a read the map sends a page wide takes a word muir
# never had and MD says so on the microcycle it happens.
#
# THE PROPERTY IS LIVE IN THE BOOT PROM, measured against muir and against
# CLAUDE.md, which said it was not: `SET-UP-FOUR-PAGES` writes four
# second-level entries at microcycles 536,290, 536,293, 536,297 and 536,299,
# each from ZERO --- no access --- to MAP-ACCESS-CODE 3, and the first bus
# cycle is at 536,302.  Twelve microcycles after the first and three after the
# last.  `PDL-BUFFER-REFILL`'s `((VMA-WRITE-MAP) IOR M-PGF-TEM ...)` is seven
# microcycles ahead of `P-R-1`, which is where the board halted on 2026-09-10;
# this is the same shape on a program that needs no pack.
#
# WHAT THIS PROGRAM CANNOT REACH, so that nobody files it as a hole: muir
# refuses the access on NONE of the 600,000 microcycles, and every map word the
# boot PROM writes has MAP-ACCESS-CODE 3 --- bits 23 and 22 alike.  So -VMAOK
# is compared only in its permitted direction and the two access bits cannot be
# told from each other.  `the-access-bits-swap-halves` below is that
# equivalence, measured, with the record that stands in its place.

@note one entry along, the entry the program then reads through stands at the

@note
@note This is what `PDL-BUFFER-REFILL` would see if its map hack did not take,
