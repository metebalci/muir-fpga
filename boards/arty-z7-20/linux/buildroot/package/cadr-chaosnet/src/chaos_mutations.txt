# The mutation list for cadr-chaosnet: bugs `chaos_test` has to catch.
#
# `mutate.py` applies each record to a copy of this package's sources, builds
# the check against it, and runs it.  A mutation the check FAILS on is a check
# doing its job; one the check passes is reported as SURVIVED and the run is
# red.  A record whose `@old` no longer matches its file exactly once, or that
# does not compile, is BROKEN and also fails the run --- two fabric mutations
# were once reported as surviving that had never been built.
#
# THE FORMAT is `mutations/list.txt`'s, so that anybody who has read that one
# can read this one:
#
#   @mutation  a kebab-case name; how a survivor is reported
#   @file      which of this package's core sources to mutate
#   @why       what the check is supposed to notice, printed when it does not
#   @note      prose, repeatable; printed with @why on a survivor
#   @old       the source to replace, exactly as it stands
#   @new       what to put there; empty deletes
#   @end
#
# WHERE THE LIST CAME FROM.  One record for every decision this program makes
# that a reader would otherwise have to take on trust, grouped by the layer it
# is in: the packet's own arithmetic, the register face's handshake with the
# fabric, and CHUDP's frame.  Those three layers are the whole program.
#
# **FORTY-NINE RECORDS WENT WHEN THE SERVICES DID.**  This list held four
# records for the connection protocol, three for the TIME, UPTIME and STATUS
# answers and forty-two for the FILE service.  A CADR has no file or time
# server in it, muir removed its own at `79c7590`, and so this program has
# none: the host is on the network.  A record for code that should not exist
# is not a record, so they went with the code rather than being kept as a
# list of bugs in a program nobody runs.
#
# **THE CHECK WORD HAS A REAL ANCHOR AND THAT IS WHY ITS RECORDS ARE WORTH
# HAVING.**  muir's `tests/chaos.rs` pins `135771` as the word the NETLIST
# BOARD itself produced for a particular twelve words, and says that of the
# 9401's polynomials, its two bit orders and its two seeds, only one
# arrangement gives it.  `chaos_test_packet` holds this C to that number.  So
# a mutation of the polynomial is not caught by a round trip agreeing with
# itself --- which it would, both ends being wrong together --- but by
# disagreeing with a measurement off real hardware.

@mutation the-check-word-polynomial-loses-a-tap
@file chaos_packet.c
@why the check word against 135771, which is what the netlist board produced for muir's twelve words
@note The 9401's CRC-16 is x^16 + x^15 + x^2 + 1.  Dropping the x^2 term
@note leaves a polynomial that is still a CRC and still round-trips against
@note itself, so only the board's own figure catches it.
@old
				next ^= 1u | (1u << 2) | (1u << 15);
@new
				next ^= 1u | (1u << 15);
@end

@mutation the-check-word-shifts-least-significant-bit-first
@file chaos_packet.c
@why the check word against 135771: the two 74165s at LMTBUF B12 and B13 shift a word out most-significant bit first, and the other order gives a different word
@note muir's packet.rs says this bit order is not read off a document --- it
@note is the one arrangement of the orders, seeds and polynomials the 9401
@note offers that reproduces the board's own output.
@old
		for (int k = 15; k >= 0; --k) {
@new
		for (int k = 0; k <= 15; ++k) {
@end

@mutation the-data-bytes-go-high-half-first
@file chaos_packet.c
@why the packet's words against muir's own literals: AIM-628 section 3.6 puts the first byte of a pair in the arithmetically LEAST significant position
@note "TIME" is 044524 044515 in muir's test and would be 052104 015515
@note swapped.  A round trip alone would not see it, because the reader here
@note would unswap what the writer swapped.
@old
			(uint16_t)(p->data[lo] |
				   ((hi < p->len ? (unsigned)p->data[hi] : 0u) << 8));
@new
			(uint16_t)(((unsigned)p->data[lo] << 8) |
				   (hi < p->len ? (unsigned)p->data[hi] : 0u));
@end

@mutation an-odd-byte-count-loses-its-last-byte
@file chaos_packet.c
@why a packet of five bytes: the data is a whole number of WORDS on the cable, so an odd count rounds UP and the spare half is padding
@note AIM-628 section 7: an odd last byte "sits in the low half with a
@note garbage padding byte in its high half".  Rounding down silently drops
@note the last byte of every odd-length packet, which is most text.
@old
	const unsigned data_words = ((unsigned)p->len + 1u) / 2u;
@new
	const unsigned data_words = (unsigned)p->len / 2u;
@end

@mutation the-check-word-is-computed-over-itself
@file chaos_packet.c
@why the frame's check word against 135771: the word covers the buffer and the source the hardware adds, and stops there
@old
	out[n + 2] = chaos_check_word(out, n + 2);
@new
	out[n + 2] = chaos_check_word(out, n + 1);
@end

@mutation a-frame-with-a-wrong-check-word-is-called-good
@file chaos_packet.c
@why a frame whose check word does not match must come back with check_ok clear, because that is the only thing between a corrupted packet and the transport acting on it
@note The interface has a CRC Error bit for exactly this and AIM-628 section
@note 5.1 meters it.  A parser that always says the frame is good turns every
@note line error into a packet the NCP believes.
@old
	out->check_ok = chaos_check_word(words, body + 2) == out->check;
@new
	out->check_ok = 1;
@end

@mutation the-data-count-is-not-held-against-the-frames-length

@why a frame whose 12-bit count disagrees with the number of words it actually carries must be refused, not read past its end
@note AIM-628 section 5.1 meters incoming packets "rejected for a length that

@note parser reads the trailer as data, or data as the trailer.
@old

@new

@mutation the-forwarding-count-eats-the-byte-count
@file chaos_packet.c
@why the count word is the forwarding count in bits 15:12 and the byte count in 11:0, and a mask of 017777 lets a forwarding count of 1 read as 4096 bytes

# ---- Chaosnet over UDP ----

# **THE FRAMING IS `cbridge`'S AND THESE RECORDS ARE WHAT HOLD IT THERE.**
# Every 16-bit word goes most significant byte first, the data therefore comes
# out swapped in pairs, an odd count is padded, and the trailer's third word
# is the Internet checksum and not the CADR's CRC-16.  Each of those is a
# record below, and each is caught against bytes `cbridge` accepted or a
# datagram `cbridge` sent rather than against this program's own arithmetic
# agreeing with itself --- which is why the two vectors in `chaos_test_udp.c`
# are pinned as literal bytes.

@mutation the-chudp-packets-words-go-out-least-significant-byte-first
@file chaos_udp.h
@why every 16-bit word of a CHUDP datagram goes most significant byte first, the packet's own words among them: `STATUS` is `TSTASU` on the wire, and the other order is what `cbridge` rejects as bogus with the opcode read as 0
@note This is the framing this program spoke before `cbridge` was run and
@note watched.  Both ends of a round trip move together under it, so nothing
@note but a datagram pinned as literal bytes catches it --- which is what the
@note two vectors in the check are for.
@old
#define CHUDP_PACKET_ORDER  CHUDP_BIG
@new
#define CHUDP_PACKET_ORDER  CHUDP_LITTLE
@end

@mutation the-chudp-trailer-goes-out-least-significant-byte-first
@file chaos_udp.h
@why the trailer's three words are in the same order as everything else, so the addresses in them read as addresses and the checksum as a checksum
@note The two constants are kept separate because a version 2 of the protocol
@note may differ from version 1 in nothing but byte order.  Separate names
@note that nothing distinguishes would be two ways to write one fact, so each
@note has a record of its own.
@old
#define CHUDP_TRAILER_ORDER CHUDP_BIG
@new
#define CHUDP_TRAILER_ORDER CHUDP_LITTLE
@end

@mutation the-checksum-does-not-fold-its-carry
@file chaos_udp.c
@why the trailer carries an INTERNET checksum, whose sum is in one's complement arithmetic: the carry out of sixteen bits is added back in
@note This one is worth its place because it is small.  Over the pinned RFC
@note the unfolded sum gives 0xEA6E where the checksum is 0xEA6D --- one ---
@note and a frame carrying it is dropped by `cbridge` and by everything else
@note that checks.  A round trip against itself would never see it.
@old
		sum = (sum & 0xffffu) + (sum >> 16);
@new
@end

@mutation the-checksum-is-a-plain-sum-and-not-its-complement
@file chaos_udp.c
@why the checksum is the one's COMPLEMENT of the one's complement sum, which is what makes a whole frame, the checksum among them, sum to 0xFFFF
@note Without the complement the pinned RFC carries 0x1592 where `cbridge`
@note wants 0xEA6D, and `chudp_checksum_ok` then refuses every frame that is
@note good and takes one whose words sum to zero.
@old
	return (uint16_t)(~sum & 0xffffu);
@new
	return (uint16_t)(sum & 0xffffu);
@end

@mutation the-checksum-leaves-the-trailers-two-addresses-out
@file chaos_udp.c
@why the checksum is over EVERY word before it --- the eight header words, the data words, and the trailer's destination and source --- so that a next hop damaged in flight is caught
@note The trailer's destination is the next hop and is the one word a bridge
@note routes on, so leaving it uncovered is the worst of the three places
@note this could go wrong.  Over the pinned RFC it gives 0xF6B5.
@old
	put_word(CHUDP_TRAILER_ORDER, chudp_checksum(words, body + 2u),
@new
	put_word(CHUDP_TRAILER_ORDER, chudp_checksum(words, body),
@end

@mutation a-frame-whose-words-do-not-sum-right-is-carried-anyway
@file chaos_udp.c
@why a bad checksum is DROPPED, as `cbridge` drops one: carrying the frame would mean handing the machine a check word this program made for it, and the machine has no other way to know the frame was damaged
@note The interface's CRC Error bit is held low on this board for want of a
@note seam bit to carry it, so a damaged frame carried here reaches the
@note machine looking whole.  That is the one failure a link must not have.
@old
		*bad_checksum = 1;
		return 0;
	}
@new
		*bad_checksum = 1;
	}
@end

@mutation the-machines-own-check-word-is-not-made-for-an-arriving-frame
@file chaos_udp.c
@why the trailer's third word is the Internet checksum on the wire and the 9401's CRC-16 on the machine's seam, and the machine reads the trailer's three words back out of its own buffer
@note The fabric computes that word on transmit and computes none on
@note receipt, so this line is where an arriving frame's comes from.  Without
@note it the machine is handed a checksum where its own check word belongs,
@note and every frame off the network looks damaged to anything that verifies
@note it.
@old
	out[n - 1u] = chaos_check_word(out, n - 1u);
@new
@end

@mutation an-odd-data-count-is-not-padded-to-a-whole-word
@file chaos_udp.c
@why the data is whole 16-bit words on the cable, so an odd count is padded, and a datagram carrying the padding is the one this reads
@note `cbridge` always pads.  Holding the length to the bare count refuses
@note every packet with an odd number of data bytes, which is half of them.
@old
	if (body != CHUDP_SOFTWARE_HEADER + ((count + 1u) & ~1u)) {
@new
	if (body != CHUDP_SOFTWARE_HEADER + count) {
@end

@mutation an-unpadded-odd-count-is-read-and-its-last-byte-guessed-at
@file chaos_udp.c
@why an unpadded odd count is refused BY NAME: its lone trailing byte sits exactly where the pad byte would be, so whether it is data or padding cannot be told from the datagram
@note Being liberal here looks harmless and is not.  The byte is read as the
@note half that comes first on the wire, which for an odd count is the
@note padding and never the data, so the packet handed on is wrong in its
@note last byte and in its count together --- and the checksum then refuses
@note it for the wrong reason, which is what this record catches.
@old
	if (body != CHUDP_SOFTWARE_HEADER + ((count + 1u) & ~1u)) {
@new
	if (body != CHUDP_SOFTWARE_HEADER + ((count + 1u) & ~1u) &&
	    body != CHUDP_SOFTWARE_HEADER + count) {
@end

@mutation an-unknown-chudp-function-is-read-as-a-packet
@file chaos_udp.c
@why a datagram whose function is not "here is a Chaos packet" is refused, that being the only function defined
@note The version and the function are the two bytes that say a datagram is
@note one of ours at all.  A record for each, so neither can be left testing
@note nothing.
@old
	if (datagram[1] != CHUDP_FUNCTION_PACKET) {
@new
	if (datagram[1] == 0xFEu) {
@end

@mutation an-unknown-chudp-version-is-read-as-this-one
@file chaos_udp.c
@why a datagram carrying a version this does not speak is refused WITH ITS NUMBER, not parsed as version 1
@note The protocol's author has said a version 2 may differ from version 1 in
@note nothing but byte order, so a version 2 peer read as a version 1 one
@note would exchange nonsense rather than fail --- which is the one failure
@note mode a wire protocol must not have.
@old
	if (datagram[0] != CHUDP_VERSION) {
@new
	if (datagram[0] == 0xFFu) {
@end

# ---- the route of last resort, and the table nobody writes ----
#
# muir removed `--chaos-udp-dynamic` and added `--chaos-udp-default-peer` at
# its own `d6eac6d`, and these records hold this program to the same six
# decisions.  Each is one the reader would otherwise have to take on trust:
# where a frame goes that no peer entry names, where a broadcast does not go,
# that the default peer does not stand in front of a named one, that a frame
# for this cable's own address goes nowhere, that a datagram is judged by what
# is in it and not by the socket it came off, and that nothing on this cable
# can be impersonated by a datagram claiming its address.

@mutation the-default-peer-is-never-reached
@file chaos_udp.c
@why a frame whose destination no peer entry names goes to the default peer, which is the route of last resort and the only routing this program has
@note A peer entry says that ONE address lives at ONE endpoint, so naming a
@note bridge as a peer does not let this board talk through it: before the
@note default peer, a frame for any other address was dropped.  Delete the
@note fallback and the board is back to talking only to hosts it was told
@note about by name, which is the fault the flag exists to fix.
@old

@new
	if (0 && cable_dest != 0 && u->have_default) {
@end

@mutation the-default-peer-is-handed-a-broadcast
@file chaos_udp.c
@why a broadcast goes to the named peers alone: they are stations on this machine's own cable, and the default peer is the way out to a wider network
@note Handing a bridge a broadcast would put this cable's broadcast on a
@note network it was never meant to reach.  muir decided this deliberately and
@note says so at the function; a record is what stops somebody deciding the
@note other way by accident, since the peers still get it either way and
@note nothing else would show.
@old

@new

@end

@mutation the-default-peer-stands-in-front-of-a-named-one
@file chaos_udp.c
@why the default peer is where what is NOT named goes, not a route in front of the names: an endpoint a flag gave is where that address is reached, bridge or no bridge
@note The frame still reaches the peer, so the peer's end of the check sees
@note nothing wrong; what this catches is the copy the bridge should never
@note have been given.  A board that sent every frame to the bridge as well
@note would work and would leak every packet onto the wider network.
@old

@new

@end

# **THE COUNTERS, AND WHY THE IDENTITY IS WHAT THE RECORDS AIM AT.**  The link
# refuses a datagram for eight reasons and counted one of them, so a report
# line reading "0 in, 0 with a bad checksum" said the same thing whether
# nothing had arrived or everything had arrived and been thrown away.  The
# four counts close --- what arrived equals what came in plus the three ways
# it can fail to --- and `chaos_test_udp` drives every road once and adds them
# up.  Three of the records below break the sum and one keeps it, which is the
# one that says why the classes are asserted separately as well.

@mutation a-refusal-for-its-shape-is-counted-nowhere
@file chaos_udp.c
@why every datagram that arrives is accounted for: what arrived must equal what came in plus the three ways it can fail to
@note This is the program as it was before the counters: a bad checksum was
@note counted and the six shape rules were printed under `--chaos-trace` and
@note nowhere else.  A link refusing every datagram it heard then reported
@note nothing at all, which is exactly what a link hearing nothing reports.
@old
			bump(bad_checksum ? &u->bad_checksum : &u->bad_shape);
@new
			if (bad_checksum)
				bump(&u->bad_checksum);
@end

@mutation the-arrival-is-counted-after-the-refusal
@file chaos_udp.c
@why the arrival is counted at the socket, before anything has looked at the datagram, or the sum does not close
@note The natural place to put this count is beside the delivery, where the
@note frame is in hand --- and there it counts the datagrams that came in
@note rather than the datagrams that arrived, so the refusals are no longer a
@note part of anything and the line stops adding up.  Counting at the socket
@note is what makes every road below it accountable.
@old
		bump(&u->received);
		uint16_t words[CHAOS_PKT_MAX_WORDS];
		const char *why = NULL;
		int bad_checksum = 0;
		const unsigned n = chudp_unwrap(datagram, (unsigned)got, words,
						CHAOS_PKT_MAX_WORDS, &why, &bad_checksum);
@new
		uint16_t words[CHAOS_PKT_MAX_WORDS];
		const char *why = NULL;
		int bad_checksum = 0;
		const unsigned n = chudp_unwrap(datagram, (unsigned)got, words,
						CHAOS_PKT_MAX_WORDS, &why, &bad_checksum);
		if (n != 0)
			bump(&u->received);
@end

# **THE TRACE, SWITCHED WHILE THE PROGRAM RUNS.**  A board restarted to get a
# diagnostic is a board whose Lisp is lost to get it, so SIGUSR1 turns the
# trace on and SIGUSR2 off.  What the three records below hold is that the two
# signals mean different things, that a run started with the flag is not
# turned off by its own first pass, and that nothing is said when nothing
# changed.

@mutation the-two-signals-mean-the-same-thing
@file chaos_udp.c
@why SIGUSR1 turns the trace on and SIGUSR2 turns it off, and a trace that cannot be turned off fills a log
@note The handler does the one thing a handler may, which is write a flag;
@note what it writes is the whole of the difference between the two signals.
@old
	trace_asked = (sig == SIGUSR1);
@new
	trace_asked = 1;
@end

@mutation a-run-started-with-the-flag-is-turned-off-by-its-own-loop
@file chaos_udp.c
@why -1 is nothing asked, so that the first pass of the loop does not turn off a trace the flag asked for
@note The flag sets the trace before the loop begins.  If nothing asked for
@note anything is read as asking for `off`, `--chaos-trace` works until the
@note program's first idle turn and then stops, which reads as a trace that
@note misses the very packets somebody started the run to see.
@old
static volatile sig_atomic_t trace_asked = -1;
@new
static volatile sig_atomic_t trace_asked = 0;
@end

@mutation the-trace-says-a-line-every-time-it-is-asked
@file chaos_udp.c
@why one line at the change and none otherwise, so that asking twice is not two lines
@note `cadr-console trace-chaos on` is a thing somebody types when they are
@note not sure whether they typed it already.  Without the second half of
@note this test the answer is a line a pass of the loop --- a thousand a
@note second into the log the trace itself is writing to.
@old
	if (want < 0 || want == (now_on != 0))
		return -1;
@new
	if (want < 0)
		return -1;
@end
