#
# The mutation list for cadr-chaosnet: bugs `chaos_test` has to catch.
#
# `mutate.py` applies each record to a copy of this package's sources, builds
# the check against it, and runs it.  A mutation the check FAILS on is a check
# doing its job; one the check passes is reported as SURVIVED and the run is
# red.  A record whose `@old` no longer matches its file exactly once, or that
# does not compile, is BROKEN and also fails the run --- CLAUDE.md records two
# fabric mutations reported as surviving that had never been built.
#
# THE FORMAT is `mutations/list.txt`'s, so that anybody who has read that one
# can read this one:
#
#   @mutation  a kebab-case name; how a survivor is reported
#   @file      which of this package's core sources to mutate
#   @why       what the check is supposed to notice, printed when it does not
#   @note      prose, repeatable; printed with @why on a survivor
#   @old       the source to replace, exactly as it stands
#   @new       what to put there; empty deletes
#   @end
#
# WHERE THE LIST CAME FROM.  One record for every decision this program makes
# that a reader would otherwise have to take on trust, grouped by the layer it
# is in: the packet's own arithmetic, the transport of AIM-628 chapters 3 and
# 4, the services' answer formats, CHUDP's frame, and the register face's
# handshake with the fabric.
#
# **THE CHECK WORD HAS A REAL ANCHOR AND THAT IS WHY ITS RECORDS ARE WORTH
# HAVING.**  muir's `tests/chaos.rs` pins `135771` as the word the NETLIST
# BOARD itself produced for a particular twelve words, and says that of the
# 9401's polynomials, its two bit orders and its two seeds, only one
# arrangement gives it.  `chaos_test_packet` holds this C to that number.  So
# a mutation of the polynomial is not caught by a round trip agreeing with
# itself --- which it would, both ends being wrong together --- but by
# disagreeing with a measurement off real hardware.

@mutation the-check-word-polynomial-loses-a-tap
@file chaos_packet.c
@why the check word against 135771, which is what the netlist board produced for muir's twelve words
@note The 9401's CRC-16 is x^16 + x^15 + x^2 + 1.  Dropping the x^2 term
@note leaves a polynomial that is still a CRC and still round-trips against
@note itself, so only the board's own figure catches it.
@old
				next ^= 1u | (1u << 2) | (1u << 15);
@new
				next ^= 1u | (1u << 15);
@end

@mutation the-check-word-shifts-least-significant-bit-first
@file chaos_packet.c
@why the check word against 135771: the two 74165s at LMTBUF B12 and B13 shift a word out most-significant bit first, and the other order gives a different word
@note muir's packet.rs says this bit order is not read off a document --- it
@note is the one arrangement of the orders, seeds and polynomials the 9401
@note offers that reproduces the board's own output.
@old
		for (int k = 15; k >= 0; --k) {
@new
		for (int k = 0; k <= 15; ++k) {
@end

@mutation the-data-bytes-go-high-half-first
@file chaos_packet.c
@why the packet's words against muir's own literals: AIM-628 section 3.6 puts the first byte of a pair in the arithmetically LEAST significant position
@note "TIME" is 044524 044515 in muir's test and would be 052104 015515
@note swapped.  A round trip alone would not see it, because the reader here
@note would unswap what the writer swapped.
@old
			(uint16_t)(p->data[lo] |
				   ((hi < p->len ? (unsigned)p->data[hi] : 0u) << 8));
@new
			(uint16_t)(((unsigned)p->data[lo] << 8) |
				   (hi < p->len ? (unsigned)p->data[hi] : 0u));
@end

@mutation an-odd-byte-count-loses-its-last-byte
@file chaos_packet.c
@why a packet of five bytes: the data is a whole number of WORDS on the cable, so an odd count rounds UP and the spare half is padding
@note AIM-628 section 7: an odd last byte "sits in the low half with a
@note garbage padding byte in its high half".  Rounding down silently drops
@note the last byte of every odd-length packet, which is most text.
@old
	const unsigned data_words = ((unsigned)p->len + 1u) / 2u;
@new
	const unsigned data_words = (unsigned)p->len / 2u;
@end

@mutation the-check-word-is-computed-over-itself
@file chaos_packet.c
@why the frame's check word against 135771: the word covers the buffer and the source the hardware adds, and stops there
@old
	out[n + 2] = chaos_check_word(out, n + 2);
@new
	out[n + 2] = chaos_check_word(out, n + 1);
@end

@mutation a-frame-with-a-wrong-check-word-is-called-good
@file chaos_packet.c
@why a frame whose check word does not match must come back with check_ok clear, because that is the only thing between a corrupted packet and the transport acting on it
@note The interface has a CRC Error bit for exactly this and AIM-628 section
@note 5.1 meters it.  A parser that always says the frame is good turns every
@note line error into a packet the NCP believes.
@old
	out->check_ok = chaos_check_word(words, body + 2) == out->check;
@new
	out->check_ok = 1;
@end

@mutation the-data-count-is-not-held-against-the-frames-length
@file chaos_packet.c
@why a frame whose 12-bit count disagrees with the number of words it actually carries must be refused, not read past its end
@note AIM-628 section 5.1 meters incoming packets "rejected for a length that
@note is not a multiple of 16 bits" and its neighbours.  Without this the
@note parser reads the trailer as data, or data as the trailer.
@old
	if (body != CHAOS_PKT_HEADER_WORDS + (count + 1u) / 2u) {
@new
	if (body < CHAOS_PKT_HEADER_WORDS) {
@end

@mutation the-forwarding-count-eats-the-byte-count
@file chaos_packet.c
@why the count word is the forwarding count in bits 15:12 and the byte count in 11:0, and a mask of 017777 lets a forwarding count of 1 read as 4096 bytes
@old
	const unsigned count = words[1] & 07777u;
@new
	const unsigned count = words[1] & 017777u;
@end

@mutation the-retransmission-interval-is-twice-what-the-memo-says
@file chaos_ncp.c
@why AIM-628 section 3.8: "Retransmission occurs every 1/2 second", and a check that cannot tell the constant from twice it cannot tell it from anything

@note check still drifts.
@old

@new

@mutation a-silent-connection-is-never-given-up
@file chaos_ncp.c
@why a connection whose peer has stopped answering must be given up after the band's own HOST-DOWN-INTERVAL, or its index shadows the RFC a rebooted band sends on the same index
@note muir's rfc() expires first for exactly this reason: a reboot of the
@note same band reuses the index while the old connection is still in the
@note table, and the fresh RFC is then taken for a duplicate and dropped.
@old

# ---- the FILE service ----
#
# **THE CONTAINMENT RECORDS ARE THE ONES THAT MATTER MOST HERE.**  This
# service reads, writes, renames and deletes a real directory on the board at
# the asking of whatever is on the Chaosnet, so the rule that a pathname
# cannot leave the tree is the whole of what makes that safe.  It is also the
# kind of rule that keeps working by accident after it has been broken --- a
# `..` that goes nowhere because the root happens to be deep --- so it is
# mutated in both of the two ways it can fail.

@mutation the-containment-follows-dot-dot
@file chaos_file.c
@why `..` and `.` in a pathname are REFUSED and not followed, so that no client on the cable can walk out of the tree the board serves
@note muir's resolve() says why refusing beats following: "following them is
@note how a containment rule is got wrong, and a client with a legitimate use
@note for either can spell the place it means".
@old
		if ((len == 2 && s[0] == '.' && s[1] == '.') ||
		    (len == 1 && s[0] == '.'))
			return -1;
@new
		if (len == 1 && s[0] == '.')
			return -1;
@end

@mutation a-link-that-leads-out-of-the-tree-is-followed
@file chaos_file.c
@why a resolved path must lie under the root or under what one of the ROOT'S OWN entries links to; a link made deeper that leads out is refused
@note The root's own links are how a release tree is served --- `sys` for
@note System 304 and `tree` for System 100 --- so the rule cannot be "under
@note the root" alone, and the part that is easy to lose is the part that
@note stops a CREATE-LINK widening the tree.
@old
		if (under(real, tree.paths[i])) {
@new
		if (real != NULL) {
@end

@mutation the-lisp-machines-newline-is-not-translated-on-the-way-out
@file chaos_file.c
@why a file read off the board arrives at the band with 0215 where Unix has a newline; leaving 012 alone hands the band a character it does not use as a line break
@note `#/NEWLINE` is 0215 and the Lisp Machine's own carriage return is a
@note real 015, which is why this is a translation and not a pass-through.
@old
		case '\n':
			out[i] = CHAOS_FILE_NEWLINE;
			break;
@new
		case '\n':
			out[i] = '\n';
			break;
@end

# ---- the FILE service, in depth ----
#
# **THESE THIRTY-NINE CAME FROM A SWEEP, NOT FROM A LIST WRITTEN IN ADVANCE,
# AND SEVEN OF THEM SURVIVED THE FIRST TIME.**  The FILE check passed every
# one of its own assertions on its first run, which this project distrusts on
# principle, so every decision `chaos_file.c` makes was mutated and the check
# re-run.  Seven survived, and each was a real hole rather than an equivalent
# mutant: a containment test written as a string prefix where muir's is
# component-wise (the trap the C port creates and the Rust cannot have); a
# read that drains another handle's bytes, which is muir's own afternoon-long
# bug and only shows with a turn of the server between the data and the CLOSE;
# a FILEPOS that keeps what is already in flight, which only shows with NO
# turn between the OPEN and the FILEPOS, because that is what the client
# sends; the home directory's case; the blank line between directory records;
# a reused file handle; and the asynchronous mark's `R` severity, which had no
# check at all until this and made the whole stalled-write path get one.
#
# So the list below is what the check was WEAK at, written down, and the
# check is stronger by exactly those seven.  That is the argument for sweeping
# rather than for listing: a list written in advance holds what its author
# already thought of.

@file chaos_file.c
@why a single `.` component is refused too, not just `..`
@note muir refuses both in one test.  Refusing `..` alone leaves `.` as a way
@note to spell a path the resolver then canonicalises differently from the way
@note it was checked.
@old

@new

@end

@mutation the-roots-own-links-are-not-followed
@file chaos_file.c
@why a symlink AT THE ROOT must be followed, because that is how a release tree is served
@note Each release's fetch script puts its sources under the root by such a
@note link --- `sys` for System 304 and `tree` for System 100 --- so a
@note containment rule that refuses them serves an empty tree.
@old

			if (real)

@new

@end

@mutation a-prefix-match-instead-of-a-component-match
@file chaos_file.c
@why the tree test is COMPONENT-WISE, and a plain string prefix lets a directory whose name merely starts with the root's pass
@note Rust's `Path::starts_with` is component-wise and C's `strncmp` is not,
@note so this is the trap the port itself creates and muir cannot have.  A
@note sibling called `servedmore` beside a root called `served` is the case.

@end
